# 手順書のディレクトリ設計

作成日：2026-10-15  
更新日：2026-10-15  
状態：現在の配置を整理済み。拡張構成は、今後の執筆に向けた配置計画。

## 1. 分離の基準

文書を読む目的によって、次の二つに分けます。

| 配置先 | 主な読者 | 置く内容 |
| --- | --- | --- |
| `authoring/` | 手順書の作成者・改善担当者 | 作成方針、構成の判断理由、未決事項、将来への引き継ぎ、手順書の検証記録 |
| `manual/` | アプリケーションの開発者 | 実行する手順、判断基準、参考・詳細資料、ツール別・アプリ種別の補足、テンプレート、記入例 |

`authoring` は「手順書の執筆・編集」、`manual` は「実際に利用する手順書」を表す名前として採用します。共通の親を `spec-driven/` とすることで、このテーマに関係する文書をまとめて管理できます。

手順書を管理するリポジトリと、題材アプリを開発するリポジトリも区別します。

| 作業場所 | 管理・実行するもの |
| --- | --- |
| このリポジトリの `spec-driven/` | 方針文書、手順書、読者向けのプロンプト・記入例、手順書の検証記録 |
| 開発対象アプリのリポジトリ | アプリ用の `AGENTS.md`、仕様・設計、ソース、テスト、Go 製の支援ツールと依存、`Taskfile.yml`、hooks・CI の設定、ビルド・リリースの操作 |

各工程で操作する作業場所を明記します。題材アプリ側の具体的な配置は、技術構成に合わせて手順書の執筆時に決めます。

| `authoring/development-workflow.md` | 新規開発の順序、AGENTS.md・hooks の配置、テスト仕様と承認、手動評価の14列、タグ CI、不具合修正と正式リリースの指針 |
| `authoring/directory-structure.md` | ディレクトリの役割と、文書を追加する際の配置規則 |
| `authoring/example-application.md` | 具体プロンプトと実践検証に使うメモ管理アプリの確定事項・未決事項 |
| `authoring/existing-development-notes.md` | 後で改修版を作る際に必要な情報と、新規作成版の検証中に残す記録 |
| `authoring/review-notes.md` | 手順の抜け・過剰な作業・依存関係のレビュー指摘、修正理由、実践検証へ残す確認事項 |

| `manual/README.md` | 手順書本体の入口。現段階では未執筆であることを明示 |

現在は、手順書作成のための方針文書と手順書本体の入口を配置しています。工程別の手順は、作成方針に沿って追加します。

## 3. 手順書本体を執筆する際の拡張先

### 3.1. 配置計画

以下は将来の配置計画です。`manual/README.md` 以外のファイル・ディレクトリは、対応する内容を執筆する時点で作成します。

```text

├── reference/           # 用語、考え方、判断の背景、共通の詳細説明
│   ├── agents-maintenance.md             # AGENTS.md の初期作成・更新・再読
│   ├── work-sessions-and-context.md      # 時間の区切り、引き継ぎ、会話整理・委任
│   ├── implementation-rules-and-hooks.md # 実装ルールの再確認・検査・停止
│   ├── development-tools-and-task.md     # Go 製の支援ツール、Taskfile、ホスト・CI
```

| 配置先 | 記述範囲 | 重複を避ける方法 |
| --- | --- | --- |

| `app-types/` | Web・CLI・デスクトップ固有の仕様、確認方法、成果物の違い | 共通手順に対する追加・変更箇所を示す |
| `stacks/` | Wails v2／v3、Tauri 2、WPF＋Blazor、Go CLI、React／Vue／Svelte＋Go の環境準備・実装・ビルド・配布 | アプリ種別の補足と共通の詳細資料を参照し、構成固有の差分を集約する |
| `tools/` | Codex を主とする操作例と、Claude Code へ適用する際の注意点。hooks の登録方法・イベント・失敗時の挙動も扱う | 共通の仕様・工程・実装ルールを参照し、ツールの違いを集約する |
| `prompts/generic/` | 各工程で使う汎用プロンプト。置換する値と、入力・成果物・制約・完了条件を示す | 工程の本文と、対応する具体プロンプトの参照元を明確にする |
| `templates/` | アイデア、要求・仕様、単体テスト要件、自動・手動 E2E 仕様、14列の手動評価 `.xlsx`、不具合・修正内容レポートなどのひな型 | 各工程から同じひな型を参照する。評価回ごとの記入済み結果と未記入のひな型を分ける |
| `examples/` | 題材の説明、具体プロンプト、記入済み成果物。最初はメモ管理アプリを使う | 手順書の編集上の議論は `authoring/` に残し、検証記録から読者向けの内容を整理する |

### 3.2. 共通手順と文書の役割

本編を進めるために必須の情報は、該当工程から到達できるようにします。詳細資料を探さなければ次の作業が分からない構成は避けます。

新規開発の工程は、[開発の手順指針](development-workflow.md)に従って執筆します。要求・設計・テスト仕様の承認、hooks と環境・雛形の準備、機能単位のテスト先行と実装の反復、CI の早期実行、タグ CI と RC の手動評価、不具合修正、正式版の未公開作成・確認・公開を共通本編へ反映します。上記のひな型名は配置案です。必須の14列は同指針の第6節を正本とします。

文書の役割を満たせる小規模な構成では、仕様・設計の複数の役割を一つのファイル内へまとめられます。配置計画にあるすべての文書やテスト種別を、開発対象アプリに毎回追加する扱いにはしません。利用者向けの導入・操作・復旧の説明は、対象アプリ側の `README.md` や配布資料として用意します。

### 3.3. 作業記録と技術構成別の補足

作業単位・チェックポイントの正本は、開発対象アプリ側の計画・作業記録に置きます。ここでは `manual/templates/` にひな型、`manual/reference/` に共通の使い方、`tools/` にコマンド・利用形態・版による差分を記載する計画です。各工程には30〜60分の分割、保存・再開、`/clear`・`/compact` と委任の扱いを残し、詳細は[作業単位の方針](work-session-policy.md)を参照します。

ひな型は変更分だけを追記できる形にし、環境・承認・指示などの参照は共用します。作業ごとの別ファイルや、全項目の再記入を必須にしません。レビュー・実行結果には対象版への参照を持たせ、途中の状態と工程全体の承認・完了を区別します。

技術構成と OS・CPU の基準は、[作成方針の技術構成と対象環境](creation-policy.md#12-技術構成と対象環境)を正本とします。Windows 11 amd64 を基本に説明し、アプリで対応すると決めた Ubuntu 環境の差分を補足します。WPF＋Blazor の文書は Windows 向けにします。

開発支援の詳細資料には、Go・task が導入済みのホストでの確認、Go 製の Excel 生成・検証・計測ツール、Taskfile の準備と CI での利用を記載します。[開発支援ツールの方針](creation-policy.md#123-開発支援ツールと-task)に従い、実行する Go ソース・依存とルートの `Taskfile.yml` はアプリ側で管理します。ここでの `manual/tools/` は AI エージェントの説明文書の配置先です。ひな型・説明・記入済み結果と実行コードの正本を区別し、Go ツールの配置・モジュール範囲は対象アプリの構成に合わせて具体化します。

E2E のケースは仕様書の表または付属の構造化データを一つの編集元とし、生成する Excel と説明資料で同じケースを独立して編集しません。共通の Go 生成ツールを再利用できる配置と、アプリ固有のケース・評価回・環境別の結果を分ける保存先を執筆時に決めます。事前実証のコード・条件・結果は製品実装と区別し、採用する設定だけを後続工程へ引き継ぎます。

Caddy の詳細資料では、Windows 11 amd64、Ubuntu 24.04 LTS amd64、Ubuntu 24.04 LTS arm64 のホスト別手順を扱います。導入・サービス・設定・配信・転送先・データ保存を説明し、React／Vue／Svelte＋Go の各構成から共通資料へ参照します。

HTTPS・CA の資料では、共通 Caddy の内部 CA と自動的な証明書管理、利用端末での信頼登録、CA データの継続利用を説明します。初回の準備とアプリ追加時の設定を分け、アプリごとの CA 登録を繰り返さない構成を示します。配置・役割の基準は、[共通 Caddy の方針](creation-policy.md#133-共通-caddy-の配置とホスト別の手順)を参照します。

### 3.4. プロンプトと成果物の管理

各工程の本文には、汎用プロンプトと具体プロンプトを対で掲載します。正本は `prompts/generic/` と `examples/memo-manager/prompts/` で管理し、プロンプト ID・版・本文への掲載箇所を記録します。本文のコードブロックは正本の転載として扱い、文面を修正する際は正本を変更してから掲載先へ反映します。公開・更新時に、転載した入力文と正本の一致を確認します。

中断保存・再開、圧縮前後・新しい会話への引き継ぎ、サブエージェントの起動・結果回収のプロンプトも、同じ正本の管理規則で用意します。題材の途中状態・保存先を具体版でそろえ、独立した会話だけを読んでも作業を再開できるようにします。

`templates/` は AI が作成する文書のひな型、`prompts/` は AI に入力する依頼文を置く場所として区別します。題材の選定理由・未決事項は [想定アプリケーション](example-application.md)に記録し、読者向けの実践例と分けます。

## 4. 作成側の記録を増やす場合

| 追加先の候補 | 作成するタイミング | 置く内容 |
| --- | --- | --- |
| `authoring/decisions/` | 方針の変更理由が増えたとき | 決定内容、理由、代案、影響する文書 |
| `authoring/validation/` | 手順書の実践検証を開始するとき | 使用した手順書の版、試行条件、質問の実績、つまずき、修正と再確認の記録 |

手順書を改善するための試行記録は `authoring/validation/` に置きます。試行結果を整理し、読者が参考にできる実践例にしたものは `manual/examples/` に置きます。

検証記録には、実際に Codex に入力した具体プロンプト・追加指示と、開発対象リポジトリの `AGENTS.md` の更新理由・差分・適用確認も残します。

検証した文書の版、ツール・技術構成・OS・CPU、CI 実行と RC／正式版の対応を記録します。文書のレビュー記録と、手順を実行した検証記録は区別します。

要求・設計・テスト仕様の承認記録、hooks の作成・動作確認、要求 ID からテスト結果までの対応、評価 `.xlsx` と不具合レポート、タグ送信から成果物取得までの記録も、実践検証の対象にします。

予定と実際の作業時間・待ち時間、途中保存と再開、会話の切り替え・圧縮、サブエージェントの起動・回収・停止の記録も残します。作業記録のひな型は小規模な計画と統合できる形にし、記録作業のために30〜60分の作業が大きく膨らまないかも確認します。

## 5. 配置・命名・更新の規則

- 作成方針や未決事項は `authoring/` に置き、読者が実行する工程は `manual/` に置きます。
- 全体の入口は `spec-driven/README.md`、手順書本体の入口は `manual/README.md` とします。
- 文書内の見出し・説明は日本語にします。ファイル名は内容を表す英小文字とハイフンを基本にします。
- 工程の番号は、工程の構成を決めてから付けます。参考資料やアプリ種別の補足には、通しの工程番号を付けません。
- 未作成の文書は「作成予定」と明示し、実在するファイルと区別します。
- 内容の追加に合わせてディレクトリを作成します。空のディレクトリや、内容のない文書を先に増やしません。
- 同じ決定事項の本文は一か所で管理し、他の文書から参照します。プロンプトを本文へ転載する場合は、正本と対になる配布用の写しとして管理し、独立した編集元を増やしません。
- 方針を変更した場合は、作成方針、影響する手順、テンプレート、例の整合を確認します。
