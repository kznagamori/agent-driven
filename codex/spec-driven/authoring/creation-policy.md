## 1. この文書の目的

「AI エージェントによる仕様書駆動開発の手順書」の目的・対象範囲・執筆方針・品質の判定方法を定めます。手順書の執筆時は、この文書、[開発の手順指針](development-workflow.md)、[作業単位・中断再開の方針](work-session-policy.md)、[ディレクトリ設計](directory-structure.md)を確認します。

第2節は利用者との合意事項です。「基本案」「運用案」と記した内容や未決事項は、執筆・実践検証で具体化します。判断の理由と過去の確認結果は[レビュー記録](review-notes.md)に残し、文書レビュー済みと実践検証済みを区別します。

| 用語 | この文書での意味 |
| --- | --- |
| 本編 | アプリの種類を限定しない、新規作成の共通手順 |
| 補足資料 | 参考・詳細資料と、アプリ種別・技術構成・AI エージェント別の説明 |
| ユーザー | 手順に沿って開発し、仕様の承認・成果物の評価を行う人。開発するアプリの利用者とは区別する |
| 工程／作業単位 | 工程は開発の大きな段階、作業単位は30〜60分で確認・保存できるように分割した作業 |
| 正本 | 内容を更新・確認する際に基準とする文書やデータ |

## 2. 利用者との確認で決まった事項

### 2.1. 目的と対象

| 項目 | 合意事項 |
| --- | --- |
| 目標 | 同じ進め方で、アプリケーションを確実に作成できるようにする |
| 主な利用者 | 利用者本人による個人開発を主とする。開発チームや、広く他の開発者にも参考になる内容を目指す |
| 読者の前提知識 | プログラミング・Git・CI の基礎を前提にする。記述は初心者にも分かりやすく、間違えにくいものにする |
| 最初に作る手順書 | 新規アプリケーションの作成 |
| 次の展開 | 新規作成の手順書が問題ない品質になった後、既存アプリケーションの機能追加・改修を扱う手順書を作る。そのための情報も残す |
| アプリの対象 | 種類を限定しない共通の進め方を本編にする。参考・詳細資料と、Web アプリ・CLI・デスクトップアプリ向けの文書も作る |
| 完成までの範囲 | 公開・配布できる成果物と、その公開・配布手順まで扱う |
| 手順書の品質確認 | 内容のレビューに加え、代表的なデスクトップアプリを一つ、手順書に沿って作成・リリースして検証する |

### 2.2. 作業時間と対話

| 項目 | 合意事項 |
| --- | --- |
| 作業時間と粒度 | 平日は1〜4時間。大きな工程を30〜60分で保存・終了できる作業単位へ分割する。工程番号ごとの全成果物を1時間で完成させる扱いにはしない |
| 中断と再開 | 作業単位の途中でも中断でき、保存した文書・差分・確認結果・次の操作から再開できるようにする |
| AI のコンテキストと委任 | 各工程で `/clear`・`/compact` を使う条件、会話の再開、サブエージェントの起動・担当・結果回収・終了を記載する |
| 開始時の入力 | 人が簡易なアイデアを用意する |
| 人と AI の役割 | AI がアイデアから要件などの仕様書を作成し、人が要件・仕様・設計などの節目で確認する |
| 過去の問題 | アイデアを要件にする際、AI の質問が発散し、止まらなくなることがあった |
| 質問の改善 | 細かな質問や類似機能に関する質問を可能な限りグループ化し、質問回数を減らす。類似機能の仕様を統一して矛盾・不整合を減らす |
| 細部の未確定事項 | 主要な要件に影響しない細部は、AI が理由付きの推奨案を仮置きし、関連項目をまとめて人が確認する |

### 2.3. 仕様・テストと AI の利用

| 項目 | 合意事項 |
| --- | --- |
| AI エージェント | Codex を主対象とする。Claude Code にも適用できるようにしたい |
| 指示ファイルの作成・更新 | `AGENTS.md` を `/init` で初期作成し、仕様書作成後、設計・実装時などの節目で見直す。更新のタイミング・内容・手順も手順書に含める |
| プロンプトの掲載 | AI に作業を依頼する各工程に、汎用プロンプトと具体プロンプトを対で掲載する。具体版は、事前に決めたアプリを作成するために Codex へ実際に入力する文面とする |
| 具体プロンプトの題材 | Go＋Wails v2 のメモ管理デスクトップアプリ。メモの登録・編集・検索・タグ・保存を扱い、共通本編の具体例と初回の実践検証に使用する |
| 実装ルールの徹底 | hooks を使って実装ルールを読み直し、逸脱を防ぐ。再確認に加え、機械的に検出できる違反を検査・停止する仕組みを検討する |
| 仕様のレビュー・承認 | 要求仕様書、各種ドキュメント、単体テスト要件仕様書、E2E テスト仕様書を AI が作成・レビューし、ユーザーが承認する。NG は修正・レビュー・再承認へ戻す |
| テストの準備順序 | 製品の実装より先に、単体テストの必須事項・禁止事項などを定める要件仕様書と、自動・手動を区分した E2E テスト仕様書を作る。承認後に単体・E2E 自動テストを作成・レビューする |
| トレーサビリティ | E2E テストに ID を付け、関連要求を追えるようにする。要求・設計・単体テスト・実行結果・不具合との対応も明確にする |
| 手動評価ファイル | E2E 手動テスト評価ファイルを `.xlsx` で作成・レビューする。指定された14列と履歴の扱いは、開発の手順指針の第6節を正本とする |

### 2.4. 技術構成と環境

| 項目 | 合意事項 |
| --- | --- |
| デスクトップの技術構成 | Go＋Wails v2／v3、Rust＋Tauri 2、C#（.NET SDK 10 以降）＋WPF＋Blazor |
| CLI の技術構成 | Go |
| Web の技術構成 | フロントエンドは React／Vue／Svelte、バックエンドは Go |
| 開発支援ツール | Excel ファイル作成、フィジビリティチェック、性能計測、その他の自作する開発支援ツールは Go で開発する |
| タスクランナー | task（go-task）を採用する。Windows 11 の日本語環境での動作に対する利用者の懸念を踏まえ、make を共通手順の前提にしない |
| 開発ホストの前提 | Go と task（go-task）はインストール済みとする。開始時に実行可否と採用版への適合を確認する |
| 基本の対象環境 | Windows 11 amd64 を必須とする。Ubuntu 24.04 以降の amd64／arm64 はアプリごとに対応要否を決める。WPF 構成は Windows 向けとする |

| 証明書の運用 | 共通 Caddy の内部 CA を複数アプリで利用し、証明書の発行・更新を Caddy に任せる。利用端末で CA を信頼登録し、アプリ追加のたびの CA 再登録を避ける |

### 2.5. 評価とリリース

| 項目 | 合意事項 |
| --- | --- |
| 開発・リリース | `develop` で開発し、ユーザーが対象コミットに RC タグを付けて GitHub に送信する。タグ CI でビルド・単体テスト・実行可能な E2E 自動テスト・成果物作成を行い、ユーザーが成果物で手動 E2E を実施する。評価完了後、ユーザーが `main` への PR・マージ・正式版タグの送信を行い、CI で正式版を作成し、確認して配布する |
| 不具合修正 | AI が不具合・修正内容レポートを作り、ユーザーがレビューする。必要なテストだけを追加・修正し、AI の修正・自動テスト・コミット、ユーザーの新しい RC タグ送信、CI、手動 E2E を繰り返す |

## 3. 目標を具体化する方針

「同じ進め方で確実に作成できる」を、執筆・検証時に判断できるよう、次の観点で具体化します。これらは本書で提案する確認観点です。

- 開始時に必要な入力と、工程ごとの成果物が分かる。
- 人が判断する事項と、AI が作業・提案する事項が分かる。
- 次の工程へ進む条件と、問題がある場合の戻り先が分かる。
- 仕様、実装するタスク、自動テスト、人の評価項目の対応を追える。
- 別のセッションでも、保存した文書から現在の状態と次の作業を把握できる。
- 30〜60分の作業単位に区切り、平日の作業時間の中で中断・再開できる。待ち時間と実作業の時間を分けて追える。
- CI が作成した RC を人が評価し、修正を経て正式リリースまで進められる。

完成は、合意した対象範囲の仕様・受け入れ条件・評価項目を満たしたことによって判定します。「バグがなくなった」は、定めた評価が完了し、その評価で検出された未解消の NG がない状態として具体化します。

## 4. 本手順書での「仕様書駆動開発」の扱い

作成上の定義案は、次のとおりです。

> 人のアイデアを、確認可能な仕様と受け入れ条件にし、その仕様を基に設計・実装・評価を進める。変更や不具合への対応では、仕様とコードと評価内容の整合を保つ。

要求仕様書、振る舞いの仕様・設計、実装タスク、単体テスト要件仕様書、E2E テスト仕様書と評価項目の役割を説明し、それぞれに必要な情報を定めます。用語と各成果物の役割は、[開発の手順指針](development-workflow.md#21-仕様設計テストの役割)に従います。文書を分ける粒度は今後検討し、小さなアプリにも適用できる構成にします。

仕様とテスト計画は全体を先にレビュー・承認し、コードは機能単位でテストを先に作って実装・確認する順序を反復します。全テストコードの一括完成や、すべての種類の設計書の作成を前提にしません。意味が変わらない文書修正のために再承認を繰り返さず、仕様・契約・期待結果などが変わる部分に再承認を求めます。[承認の基本](development-workflow.md#22-レビューと承認)に従います。

大きな工程は、文書の関連する一群や一つの機能など、保存・確認できる30〜60分の作業単位に分けます。確認・保存・引き継ぎの時間も含め、工程全体の承認・完了条件は維持します。時間内に終わらない場合は、未完了の状態と次の作業を残します。[作業単位の方針](work-session-policy.md#2-3060分の作業単位)に従います。

## 5. 人と AI の役割を記述する方針

| 場面 | 人が担うこと | AI が担うこと |
| --- | --- | --- |
| アイデア | 作りたいもの、目的、優先事項、既知の制約を伝える | 入力を整理し、必要な不足情報を特定する |
| 要求・仕様 | 目的・範囲・重要な振る舞い、推奨案を確認し、要求仕様書を承認する | 関連事項をまとめて確認し、要求・仕様・受け入れ条件を文書化してレビューする |
| 設計・計画 | 重要な選択や仕様への影響を確認し、各種ドキュメントを承認する | 仕様に基づく設計案と実装計画を作成・レビューする |
| テスト仕様・準備 | 単体テスト要件仕様書と E2E テスト仕様書を承認する | 各仕様を作成・レビューし、承認後にテストコードと手動評価ファイルを作成・レビューする |
| 実装・自動確認 | 必要な判断や、AI だけでは行えない確認を行う | 実装、テスト、結果の確認・記録、問題への対応を進める |
| RC 評価・修正 | RC タグを送信し、CI 成果物で手動 E2E を行う。NG の不具合・修正内容レポートをレビューする | レポートを作り、必要なテスト変更、修正・再発確認・コミットを行い、次の RC 評価へつなぐ |
| 正式リリース | 評価結果と条件を確認し、PR 作成・マージ・正式版タグの送信を行う。成果物を確認して配布を判断する | 必要な変更をコミットし、PR・CI の確認、RC と正式版の対応、配布に必要な記録の整理を支援する |

確認の節目は、[開発の手順指針](development-workflow.md#3-工程の順序と担当)に従います。各節目の記録方法は手順書の執筆時に具体化し、保存された仕様や評価結果を見て判断できる形にします。

実装を開始する前に、選んだ技術構成・対象環境・適用する実装ルールを明確にします。hooks による再確認と検査は、[実装ルールを徹底する方針](#11-hooks-による実装ルールの再確認と検査)に沿って具体化します。

## 6. 質問が発散しない仕組み

### 6.1. 質問の前に整理する

AI は、アイデアから読み取れる内容を整理し、不足情報を次のように扱います。

| 不足情報の種類 | 扱い |
| --- | --- |
| 目的・対象範囲・受け入れ条件や、後からの変更が大きくなる重要事項 | 人への確認が必要な項目としてまとめる |
| 主要な要件に影響しない細部 | 理由付きの推奨案を仮置きし、関連項目をまとめて確認する |
| 今回の目的・対象範囲を超える追加案 | 将来の候補として記録する。今回の要件を確定するための質問とは分ける |

重要事項と細部の判定基準は、本編で具体例を付けて説明します。

### 6.2. 関連する機能をまとめる

- 類似機能を列挙し、共通に決められる振る舞いを先に見つけます。
- 一つのテーマについて、共通ルール、理由付きの推奨案、例外として確認したい点をまとめて提示します。
- 確定した共通ルールの適用先を記録し、同じ内容を機能ごとに繰り返し質問しません。
- 異なるルールが必要な機能は、例外の理由と影響範囲を記録します。

例えば、複数の画面で削除操作がある場合、画面ごとに削除確認の有無を聞く代わりに、対象画面を示して共通の削除ルールを提案し、例外だけを確認します。これは質問形式の説明例であり、すべてのアプリに削除確認を必須とする決定ではありません。

### 6.3. 質問を終える条件を設ける

執筆時には、次を質問の終了条件として具体化します。

1. 目的、利用者、対象範囲、主要な利用の流れを確認できている。
2. 主要な振る舞いと、達成を判定する受け入れ条件が定まっている。
3. 要件を確定できない重要な未決事項が解消している。
4. 細部の推奨案が一覧化され、人が関連項目をまとめて確認できている。
5. 類似機能の共通ルールと例外に、未解消の矛盾がない。

この状態になったら、仕様のレビューへ進みます。新しい質問は、どの終了条件を満たすために必要かを説明できるものに絞ります。既に決まった内容を問い直す場合は、新しい情報や矛盾などの理由を示します。

### 6.4. 仮置きと確定を区別する

推奨案は、対象、提案内容、理由、影響する機能、確認状態を記録します。人が確認するまでは仮置きとして扱います。仕様レビューの前に、仮置きの残件と例外をまとめて提示します。

質問の予定範囲と終了条件を最初に共有し、増えた質問は既存の確認テーマへまとめられるかを先に検討します。質問回数・ラウンド数に数値の目安を設けるかは、実践検証で判断します。

### 6.5. 確認を一巡させて収束する

最初に、今回の対象範囲に必要な確認テーマを一覧にします。各テーマに、確認したい重要事項、細部の推奨案、適用する共通ルール、確認状態をまとめます。回答済みの内容は仕様案へ反映し、同じ一覧を更新して進めます。

確認を一巡したら、残った重要な未決事項と矛盾をまとめて提示します。新たな確認テーマを増やす条件は、対象範囲の受け入れ条件を決められない不足、既存の回答との矛盾、新たに判明した重要な制約がある場合とします。追加機能の提案は将来の候補へ記録します。終了条件を満たしたら、仕様案と細部の推奨案の一括レビューへ進みます。

## 7. 開発・評価・リリースの基本フロー

利用者が指定した流れを、本編では次の順序で具体化します。担当、成果物、承認時の差し戻し、元の手順との対応の詳細は、[開発の手順指針](development-workflow.md)を正本とします。

```text
簡易なアイデア
  → 開発対象リポジトリの準備・AGENTS.md の初期作成
  → アイデアのブラッシュアップ・要求仕様書の作成・AI レビュー・ユーザー承認
  → AGENTS.md の見直し・必要な差分の反映
  → 各種仕様・設計・実装計画の作成・AI レビュー・ユーザー承認
  → AGENTS.md・実装ルールの更新
  → 単体テスト要件仕様書の作成・AI レビュー・ユーザー承認
  → 自動・手動 E2E テスト仕様書の作成・AI レビュー・ユーザー承認
  → AGENTS.md の見直し・hooks の作成・レビュー・動作検証
  → 開発環境・最小のアプリ雛形・テスト環境の整備と起動・ビルド確認
  → 最初の機能の単体・E2E 自動テストの先行作成・AI レビュー
  → E2E 手動評価ファイル（.xlsx）の作成・AI レビュー
  → タグ CI の作成・公開しない早期実行・AGENTS.md の更新
  → develop で機能単位にテスト先行作成・レビュー → 実装・自動テストを反復
  → 仕様・実装・テストの全体確認・必須検査の完了
  → AI がコミット・ユーザーが RC タグを GitHub に送信
  → GitHub Actions：RC のビルド・自動テスト・成果物作成
  → ユーザーが RC 成果物を取得・導入し、手動 E2E・結果記録
      NG：レポート作成・ユーザーレビュー → 必要なテスト変更・修正
          → コミット・新 RC タグ → CI → ユーザーが再評価
      OK：評価記録の整理・変更があればコミット
  → ユーザーが develop から main への PR を作成・確認・マージ
  → ユーザーが main の正式版タグを GitHub に送信
  → GitHub Actions：正式版のビルド・自動テスト・未公開の成果物作成
  → 正式版の確認・配布条件の判定
  → 確認した同じ正式版成果物を公開・配布
  → 記録とブランチを整理して完了
```

RC は正式リリース前の候補版です。人が評価する対象と、そのソース・CI 実行・バージョンを対応付けられるようにします。CI が失敗した場合は原因を解消し、CI と成果物の確認が済んでから次の評価や配布へ進む条件を定めます。

タグをローカルに作成する操作と、GitHub への送信を区別します。RC・正式版ともにタグの送信を CI の必須契機とし、`main` へのマージだけで正式リリースした扱いにはしません。具体的な設定の根拠は、[タグ CI の方針と公式資料](development-workflow.md#91-rc-と正式版の契機)を参照します。

このフローには、新規作成中の不具合修正と再評価を含めます。既存アプリケーションの改修版を作る前でも、RC 評価で NG が出た場合の手順は初版に必要です。

### 7.1. RC の評価結果と正式版を対応付ける

- RC ごとに、仕様の版、ソースのコミット、依存関係とビルド条件、CI 実行、成果物、対象 OS・CPU、人の評価結果を対応付けます。修正後の RC は別の版として識別します。
- 評価後にソース・依存関係・実行時設定などを変えた場合は、影響する評価をやり直します。PR の更新やマージ時に入る変更も確認対象にします。
- `main` の再ビルドでは、評価済み RC とのソース内容・依存関係・ビルド条件の対応を確認します。RC／正式版のバージョン表記など、予定する差分は事前に定めます。コミットや成果物の識別子が異なる場合も、対応を記録します。
- 正式版成果物の起動・主要操作など、配布前に行う確認を定めます。想定外の差分や NG があれば配布を止め、修正・RC の再作成・再評価へ戻ります。

CI の必須契機は RC・正式版タグの GitHub への送信です。タグ名・バージョン表記、PR のマージ方法、依存関係の固定方法、正式版の確認項目、配布先は今後具体化します。評価後のコミットは変更がある場合だけ行い、動作へ影響する変更は新しい RC で再評価します。

正式版は公開前の確認ができる場所に保持し、確認したファイルを再ビルドせずに公開します。CI の作成直後にも公開しない実行で設定・環境を確認し、最終タグで初めて CI が動く状態を避けます。配布物の導入・起動・データ継続利用、利用手順、問題時の復旧も扱います。[タグ CI と配布の条件](development-workflow.md#9-タグ-ci-と正式版への移行条件)に従います。

## 8. 本編と補足資料の書き分け

- 本編はアプリの種類を限定しない共通手順とします。
- 読者が工程を進めるための入力、作業、成果物、確認方法、完了条件を明記します。
- 参考・詳細資料には、用語、判断の理由、選択肢の比較、背景をまとめます。
- Web・CLI・デスクトップ向けの文書には、共通手順への追加・変更点と具体例を示します。
- 技術構成別の補足には、Wails v2／v3、Tauri 2、WPF＋Blazor、Go CLI、各 Web フロントエンド＋Go の準備・実装・ビルド・評価の違いを示します。
- Codex 向けの具体的な操作と、Claude Code への適用に必要な差分は、ツール別の文書にまとめます。
- 実装ルールと hooks、Caddy を使う家庭内 LAN の HTTPS と共通 CA は、複数の技術構成から参照できる詳細資料にまとめます。
- テンプレートには未記入のひな型、実践例には記入済みの成果物を用意します。

各工程の記述形式は「目的 → 前提・入力 → 人と AI の作業 → 汎用プロンプト → 具体プロンプト → 成果物 → 確認・完了条件 → 問題がある場合の対応」を基本案とします。AI に作業を依頼する工程には、両方のプロンプトを掲載します。人の操作だけを行う箇所は操作手順として明示します。成果物の記入例も、工程の理解に必要な箇所へ付けます。

工程内を分けた作業単位ごとに、見込み時間、対象範囲、保存先、途中中断の方法、再開時の最初の操作、同じ会話を継続するか、`/clear`・`/compact` の候補、サブエージェントの要否を追記します。共通の運用は[作業単位・AI コンテキストの方針](work-session-policy.md)へ集約し、本編ではその工程で選ぶ扱いを明示します。

### 8.1. 汎用プロンプトと具体プロンプト

| 種類 | 目的 | 記述する内容 |
| --- | --- | --- |
| 汎用プロンプト | 別のアプリでも再利用できるようにする | アプリ名・入力文書・技術構成などの置換箇所と、依頼内容・制約・成果物・確認条件 |
| 具体プロンプト | 題材アプリの開発で Codex へ実際に入力できるようにする | 事前に決めたアプリの具体的な情報と、その工程までに確定した仕様・ファイル名・依頼内容を反映した文面 |

- 具体版は、該当工程の前提と成果物がそろった状態で、コピーして Codex に入力できるコードブロックで示します。説明文と入力する文面を分けます。
- 具体版では、アプリ名や仕様を未記入のまま残しません。作業フォルダーなど利用環境によって変わる値は、準備手順で設定する値と置換方法を明記します。認証情報・秘密鍵などはプロンプトに埋め込みません。
- 汎用版と具体版は、同じ工程の目的・制約・完了条件に対応させ、対応する組にプロンプト ID と版を付けます。正本の文面を本文へ転載し、転載を独立した別版として編集しません。公開・更新時には正本と転載の一致を確認します。
- 作業するリポジトリ、工程、参照する文書の状態、出力先を明記します。手順書の文書パスと、題材アプリのリポジトリ内のパスを区別します。
- `/init` などの Codex の操作コマンド、PowerShell で実行するコマンド、自然言語の依頼文を区別します。
- 初期化、`AGENTS.md` の更新、アイデアの整理、要件・仕様、設計、実装・テスト、RC 評価での不具合修正、再評価、正式リリースまで、連続して追えるようにします。
- 参照する文書・作業段階、期待する成果物、人の確認が必要になる条件を明記します。要件整理のプロンプトには、関連質問のグループ化、理由付き推奨案、質問の終了条件を含めます。
- AI が追加質問をした場合や期待する結果にならなかった場合は、回答・追加指示の例や戻り先を示します。AI の応答例は、想定例と実践検証で得た結果を区別します。
- 中断保存・再開、圧縮前後・新しい会話への引き継ぎ、サブエージェントの起動依頼・結果回収にも、汎用・具体プロンプトを用意します。正本・承認・未完了の確認を読み直し、今回の作業単位を越えて進めない条件を含めます。

### 8.2. 本編を執筆する前に決める題材

具体プロンプトを後付けの断片的な例にしないため、本編の執筆前に、題材アプリの目的・対象機能・技術構成・対象環境を整理します。確定した題材と未決事項は、[想定アプリケーション](example-application.md)に記録します。

共通本編では、Go＋Wails v2 のメモ管理アプリを、一つの簡易なアイデアから正式リリースまで継続して使います。最初から完成した仕様を入力する形にせず、要件・仕様・設計の各工程で確定した情報を、その後のプロンプトへ引き継ぎます。

UI・保存形式など具体版の作成に必要な残件は、本編の執筆前に理由付き推奨案をまとめて人が確認する形で収束させます。Web・CLI や別の技術構成を扱う補足でも、執筆前に題材との関係と必要な差分を決めます。

事前に決める内容は、執筆者が一貫した例題を用意するための準備情報として記録します。本編では、その決定に至る質問・回答・推奨案の確認を、該当する工程で示します。読者へ示す初期のアイデアと、その後の工程で確定する仕様・設計を区別します。

## 9. 初心者にも分かりやすく、間違えにくい記述

- 用語・略語は初出時に説明し、一つの概念には同じ名前を使います。
- 一つの手順では、実行する作業と、その結果の確認を対応付けます。
- 必須・任意・例・未決事項を区別します。
- コマンドを書く場合は、実行場所、前提環境、置換する値、期待する結果を示します。
- ブランチ、バージョン、評価対象の成果物を明示し、取り違えを防ぎます。
- 「適切に行う」「必要に応じて確認する」などの表現には、判断条件を付けます。
- 基礎操作の説明が必要な場合は、補足へのリンクと短い具体例を用意します。

## 10. Codex と Claude Code への適用方針

共通の工程・仕様・評価方法を中心に構成し、ツール固有の指示ファイル、設定、操作方法は補足にまとめます。

指示ファイルの違いは、単純なファイル名の置き換えとして扱わず、読み込み条件と適用範囲を確認します。Codex には `AGENTS.md` の探索順序や `AGENTS.override.md` の扱いが定められています。[OpenAI 公式ドキュメント：AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

2026-10-15 に確認した Claude Code の公式資料には、条件に応じて `AGENTS.md` を直接読み込む機能も記載されています。利用バージョン、`CLAUDE.md` の有無、設定によって扱いが変わるため、実際の対象環境を確認して説明します。[Claude Code 公式ドキュメント：メモリと指示ファイル](https://code.claude.com/docs/en/memory#agentsmd)

権限や実行環境も確認対象です。Codex はサンドボックスと承認ポリシー、Claude Code は権限ルールとモードなどを備えています。このため、指示ファイル名の違いに加えて、コマンド実行・確認・設定の差分も調べる方針とします。[OpenAI 公式ドキュメント：承認とセキュリティ](https://learn.chatgpt.com/docs/agent-approvals-security)、[Claude Code 公式ドキュメント：権限](https://code.claude.com/docs/en/permissions)

具体的な操作や機能は、各文書を執筆する時点で公式資料を再確認し、確認日と検証環境を記録します。今回確認した内容だけで、手順全体の互換性を検証済みとはしません。

### 10.1. `AGENTS.md` の初期作成後の更新

手順書には、開発対象のアプリケーションのリポジトリで、`AGENTS.md` を初期作成し、工程の進行に合わせて見直す手順を含めます。

初期化・更新・ビルドの操作は開発対象リポジトリで行い、手順書を管理するこのリポジトリと区別します。`/init` の例は Codex CLI への入力として示し、他の利用形態では対応する操作を確認して補足します。

Codex CLI の `/init` は、作業ディレクトリに初期の `AGENTS.md` を作成する操作です。生成結果を、実際の開発・テスト・レビュー・リリース方法に合わせて編集することも公式資料で案内されています。[OpenAI 公式ドキュメント：再利用する指示と AGENTS.md](https://learn.chatgpt.com/guides/best-practices#make-guidance-reusable-with-agentsmd)

見直しのタイミングと内容は、次を基本案にします。

| タイミング | 見直す内容 |
| --- | --- |
| リポジトリの準備・初期化 | 既存ファイルの有無を確認し、未作成なら `/init` で初期作成する。既知の目的・構成・作業ルール、Go による開発支援ツールと task の利用、ホストの前提を反映し、未決事項を区別する |
| 要件・仕様を作成・確定した後 | 仕様書の場所、参照順序、対象範囲、受け入れ条件の参照先、仕様を変更する際の進め方 |
| 技術構成・設計を決め、実装へ進む前 | ディレクトリ構成、依存方向、実装ルールの参照先、hooks、ビルド・テスト・リンターの実行方法 |
| 開発環境・標準雛形を準備した後 | 採用版、実際の生成構成、起動・最小ビルド、テスト環境、フォーマッター・リンターの設定と実行方法 |
| 単体・E2E テスト仕様の承認後 | 承認済みテスト仕様の参照先、ID の対応、必須事項・禁止事項、テストを先に作る順序 |
| hooks・テスト・CI を導入した後 | 実際の設定・Go の検査ツール・task コマンド、ルールの再確認、停止・復帰、タグ CI の実行・成果物の確認方法 |
| 実装中に構成や実行方法が変わったとき | 実在するファイルやコマンドとの整合、適用範囲、追加・廃止された規則 |
| RC 評価・不具合修正・リリースの準備 | 評価方法、再発防止として継続適用する規則、CI・ブランチ・成果物・リリース手順への参照 |

節目ごとに更新の要否を確認し、必要な差分を反映します。仕様書全文や一時的な作業ログはそれぞれの正本で管理し、`AGENTS.md` には実行に必要な規則と参照先を簡潔にまとめます。

規則や参照先に変更がない場合は更新不要とし、確認した記録を残します。見直すたびに必ずファイルを書き換える手順にはしません。

更新手順では、以下を扱います。

1. 適用される `AGENTS.md`、上位・下位ディレクトリの指示、仕様書、設計、実際のプロジェクト構成を確認する。
2. 変更が必要になった理由と、追加・修正・削除する指示を特定する。既存の合意事項や手書きの指示を確認し、整合する差分を作る。
3. `AGENTS.md` を更新し、必要に応じて詳細ルールへの参照や、適用範囲に応じたファイルの配置を整理する。既存ファイルへの反映は差分更新を基本とする。
4. リンク先、パス、コマンド、仕様・設計・hooks・CI との整合を確認する。未導入のコマンドや未検証の内容は、その状態を明記する。
5. 更新した指示と、そこで指定する適用対象の詳細ルールを Codex に明示的に再読させ、以降の作業へ適用する。hooks が参照するルールの版も整合させる。新しいセッションでの自動検出も、対象環境で確認する。
6. 変更理由と確認結果を記録し、対応する汎用・具体プロンプトや工程の説明も更新する。

Codex の指示の自動収集は起動時に行われるため、同じセッション内での更新は、再読と適用確認の手順へつなげます。[OpenAI 公式ドキュメント：指示ファイルの読み込み](https://learn.chatgpt.com/docs/agent-configuration/agents-md#how-codex-discovers-guidance)

`AGENTS.md` の更新と、hooks によるルールの再確認・検査は、連動する手順として説明します。Claude Code への適用では、指示ファイルの読み込み方法に応じた差分を補足します。

### 10.2. 会話の整理とサブエージェント

Codex CLI の `/clear`・`/compact`、会話の再開操作、サブエージェントの起動・結果回収を、各工程の作業単位へ組み込みます。コマンドの意味と各工程での使用条件、親から渡す情報、担当範囲、結果の確認と中断時の終了方法は、[AI コンテキストの運用方針](work-session-policy.md#4-clearcompact-と会話の再開)を正本とします。

同じ目的の継続中は必要に応じて `/compact`、目的と主な入力が切り替わる節目では保存後の `/clear` を候補にします。各工程で一律に実行したり、サブエージェントを必ず起動したりする手順にはしません。プロンプトの必要情報と文書の正本をファイルへ残し、圧縮・会話切り替え後にも指示・承認・現在の差分を照合します。

同じ目的での圧縮や作業単位の境界だけを理由に、サブエージェントの強制終了・起動し直しは要求しません。レビューは保存済みの対象版へ固定し、親が確認中の対象を変更しないようにします。会話の操作は、実際のユーザー操作とファイルの保存を区別して記録します。

## 11. hooks による実装ルールの再確認と検査

### 11.1. 目的と役割

実装時には hooks を使用し、適用する実装ルールを繰り返し確認する仕組みを設けます。ルールの再提示、機械検査、違反時の停止を組み合わせ、実装ルールの逸脱を防ぐ方針です。テストコードと雛形生成にも適用するため、基本は単体・E2E のテスト仕様承認後、製品の雛形・テストコード作成前に hooks の設計・作成・登録・レビュー・事前検査の動作確認を行います。設計の成立を確かめる事前実証に必要な最小の検査は、[環境準備の指針](development-workflow.md#36-リポジトリと開発環境の準備)に従い先に整備します。ツールチェーンに依存する変更後の検査は、導入後に確認します。

Codex の `AGENTS.md` は起動時に指示を読み込む仕組みです。タスク開始・再開時や、同じセッション内でルールが変わった場合の再確認は、手順と hooks の役割として具体化します。[OpenAI 公式ドキュメント：指示ファイルの読み込み](https://learn.chatgpt.com/docs/agent-configuration/agents-md#how-codex-discovers-guidance)

### 11.2. 再確認と検査の運用案

この項の頻度・検査範囲は、実現性と負担を踏まえた運用案です。対象ツールで検証し、手順書を執筆する際に具体化します。

| タイミング | 行うこと |
| --- | --- |
| 実装タスクを開始・再開するとき | 共通ルールと、技術構成・変更対象に適用されるルールの全文を読み直す |
| 会話の切り替え・圧縮の後 | 今回の指示・適用ルール・承認・残件を正本と照合する。対応するイベントと再読の方法を対象版で確認する |
| ルールの更新後や、作業対象・技術構成が変わったとき | 適用する最新版と差分を確認し、実装計画への影響を見直す |
| コードを変更する処理の直前 | 編集ツールとコマンドによる変更を対象に、適用ルールの参照状況と、変更先・操作について事前に判定できる違反を検査する |
| コード変更後 | フォーマッター、リンター、依存方向の検査、テストなど、変更内容に応じた確認を行う |
| CI・RC 作成・正式リリース前 | 必須の検査を CI でも実行し、未解消の違反があれば評価・リリースの完了条件を満たさない扱いにする |

実装ルールには、対象ファイル・適用範囲・理由・確認方法を持たせます。ルールごとに、hooks で事前に拒否できるもの、変更後や CI で検出するもの、人のレビューが必要なものを分けます。技術構成ごとの依存方向など、アーキテクチャ上の規則も決定後に検査対象へ加えます。

各編集のたびの全資料の再注入や全テストの実行は必須にしません。タスクの開始・再開・ルール更新時の全文再読、変更前の参照版と対象の検査、変更後の影響範囲の検査、機能完了時・RC 前・CI の全体検査を使い分けます。

### 11.3. hooks を設計・検証する際の条件

- `AGENTS.md` などの案内から、実装ルールの正本と適用範囲へ到達できるようにします。hooks 用にルール本文を重複管理しない構成を検討します。
- 読み込んだファイルと版を記録する方法を検討します。記録があることと、AI が内容を理解して守ったことは、別々に確認します。
- ルールの読み込み失敗や、必須検査の失敗時は、原因を解消してから作業を再開する条件を定めます。ツール側のエラー処理も含め、意図した停止が実際に働くかを確認します。
- 未読時に変更を拒否する場合は、ルールを再確認して変更を見直す手順と、再試行が無限に続かない条件を設けます。
- フックがルールを再提示した時点と、AI がその内容を読んで変更を見直す時点を区別します。実行予定の変更を見直す必要がある場合は、先にその変更を拒否し、再読・見直し後に再試行する経路を検証します。
- hooks が対象とするツール、対象外の変更経路、長時間動作するコマンド、生成ツールによる変更を確認し、適用範囲を明示します。
- 事前の拒否と、変更後の検査・フィードバックを区別します。変更後のフックで検出した場合の修正手順も記述します。
- 正常な変更、検出対象の違反、ルール更新、フックの失敗について、想定どおりに検査・停止・復帰できることを検証します。

Codex と Claude Code には `PreToolUse` などのイベントがあり、対応するツール呼び出しを拒否できます。対象経路、追加コンテキストが届くタイミング、出力の上限、失敗時の挙動に合わせて設定します。[OpenAI 公式ドキュメント：Hooks](https://learn.chatgpt.com/docs/hooks)、[Claude Code 公式ドキュメント：Hooks](https://code.claude.com/docs/en/hooks)

追加コンテキストの返却とツール呼び出しの拒否は、それぞれ対応する出力で制御します。例えば Claude Code の追加コンテキストは次のモデル呼び出しで読まれます。また、Codex の未対応の出力フィールドは、フックのエラーとして報告された後もツール実行が続く場合があります。再提示しただけ、エラーが出ただけの状態を、実行前の再読や停止ができた証拠にはしません。[Codex のフック出力](https://learn.chatgpt.com/docs/hooks#pretooluse)、[Claude Code のコンテキスト追加](https://code.claude.com/docs/en/hooks#add-context-for-claude)

通常の検査プログラムが非ゼロで終わることと、AI エージェントが変更を拒否することも区別します。例えば Codex の `PreToolUse` は対応する拒否 JSON または終了コード `2` と標準エラーの理由を使用でき、Claude Code もイベントにより終了コードの効果が異なります。内部検査の失敗・検査不能を、そのイベントで有効な拒否形式へ変換し、標準入力・標準出力・標準エラーと実際の停止を検証します。[Codex：PreToolUse](https://learn.chatgpt.com/docs/hooks#pretooluse)、[Claude Code：終了コードと出力](https://code.claude.com/docs/en/hooks#exit-code-output)（確認日：2026-10-15）。

対象環境で必要な hooks の登録・発火・拒否・復帰を確認します。雛形・テストコード作成前には事前の再確認・検査を、製品機能の実装開始前には導入済みツールに依存する変更後の検査も確認します。hooks 自身と最小の検査環境の初期作成は準備作業として区別し、ルールの明示的な再読と差分レビューで進め、検証後は hooks 自身の変更にも検査を適用します。未対応の利用形態や変更経路がある場合は、その扱いを明示してから実装へ進みます。

テストを先に作る際の未実装による想定内の失敗と、ルール違反やテストの欠陥を分けます。工程ごとの合格条件を定め、未実装テストだけを理由に準備作業が停止し続ける構成を避けます。[作成・検証の順序](development-workflow.md#4-agentsmd-と-hooks-を組み込む条件)を参照します。

設定ファイルと Go の検査ツールは、対応する手順を執筆する際に作成・検証します。機械検査が難しい仕様の解釈や設計の妥当性は、人のレビューで確認する項目として残します。

### 12.3. 開発支援ツールと task

#### 12.3.1. 対象と用途

開発のために自作する支援ツールは Go で開発します。アプリ本体は第12.1節の採用技術を使い、各言語・フレームワークの SDK、ビルド・テスト・計測ツールは必要に応じて利用します。Taskfile・CI・hooks の設定は対応する形式で記述し、呼び出す独自の処理を Go にまとめます。

| 用途 | 方針 |
| --- | --- |
| Excel ファイル作成 | Go のツールで承認済み E2E 仕様の手動ケースから `.xlsx` を生成する。14列・ID・日本語表示を確認し、記入済みの評価結果を再生成で上書きしない |
| フィジビリティチェック | 技術上の未確認点を限定した Go の検証ツールを必要な場合に作る。目的・条件・結果・採否を残し、検証用コードと製品コードを区別する |
| 性能計測 | Go の標準ベンチマークや計測用ツールを使う。Go 以外の対象は必要な専用計測手段を呼び出し、実際の対象を測る。入力データ・版・環境・条件・結果・要求の判定基準を対応付け、測定の実行成功と基準への合格を区別する |
| その他の開発支援 | データ準備、成果物・仕様の検査、hooks の独自検査など、必要な処理を Go で作る。既存の SDK や標準ツールで足りるものを作り直すことや、不要な独自ツールを増やすことは求めない |

#### 12.3.2. Taskfile の構成と実行

タスクランナーには task（go-task）を採用します。開発対象リポジトリのルートに `Taskfile.yml` を置き、準備・起動・ビルド・テスト・検査・評価ファイル生成・計測など、必要な操作の入口をそろえます。タスク名と必要な処理は執筆時に決め、`README.md`、`AGENTS.md`、hooks、CI から同じ定義を参照します。ユーザーが担当するタグ送信・PR・マージ・公開を、通常のビルド・検査タスクから自動実行しません。

Task の `deps` は並列に動くため、生成後のビルドやビルド後の E2E など、順序が必要な処理は `cmds` のタスク呼び出しで順番を定めます。同じデータ・出力先を変更する処理も、分離できなければ順番に動かします。RC 用の必須テストは Task の更新判定でタスク全体を省略せず、対象と実行結果を確認します。ビルドや生成の再利用では、ソース・依存・設定・引数・対象環境に対応した更新条件を定めます。[Task：依存関係と実行順序](https://taskfile.dev/docs/guide/dependencies)、[更新判定](https://taskfile.dev/docs/guide/up-to-date)を参照します。

Taskfile は Windows 11 amd64 の日本語環境を基本に検証し、対応する Ubuntu 環境でも確認します。日本語の入出力・ファイル名、空白を含むパス、終了コードを確認し、複雑なファイル操作や独自ロジックは Go に置きます。通常の検査失敗は非ゼロの終了コードとして task・CI に伝え、成功として扱いません。フックの拒否は第11.3節のイベント別の形式へ変換します。Task は組み込みのシェルでコマンドを実行するため、PowerShell の対話環境がそのまま使われるとは仮定しません。作業ディレクトリと必要な環境変数を明示し、OS 固有の処理を分けます。[Task 公式ドキュメント：Platforms and shells](https://taskfile.dev/docs/guide/platforms)（確認日：2026-10-15）。

#### 12.3.3. 版管理と検査対象

Go のソースと依存関係は開発対象リポジトリで版管理し、モジュールの範囲と配置は製品構成に合わせて決めます。採用した依存は `go.mod` と、生成される場合は `go.sum` で管理し、Go・task・使用ライブラリの版と実行方法を記録します。Excel 用ライブラリなどの具体的な選定は、対応する工程の執筆時に行います。[Go 公式ドキュメント：依存関係の管理](https://go.dev/doc/modules/managing-dependencies)を参照します。

製品と支援ツールの各モジュール・フロントエンドについて、実行ディレクトリと検査タスクを対応付けます。検査対象の漏れを確認し、支援ツールの重要な振る舞いも[テストの指針](development-workflow.md#5-テストを実装より先に作る際の扱い)に従って検証します。既存の Go ツールや共通の生成処理を再利用できる場合は優先し、アプリごとに同じツール・別のテスト仕様書を作り直す手順にしません。

#### 12.3.4. 実証と性能計測

フィジビリティチェックは重要な技術上の未確認点がある場合、性能計測は要求や設計判断に必要な場合に行います。すべてのアプリへ専用ツールやベンチマーク一式を課しません。性能要求がある場合は、測定環境・データ量・測定回数などを決め、実装後に測定方法を確認し、RC 評価の完了までに配布条件に対応した基準への適合を確認します。CI と利用環境の差を扱い、自動判定するなら閾値超過を検査失敗として伝えます。コマンドの正常終了や設計前の試作結果だけで、完成版の性能要求を達成したとはしません。

#### 12.3.5. 開発ホストと CI

開発ホストでは Go と task がインストール済みで PATH から実行できることを前提にし、開始時に `go version`・`task --version` で確認します。採用版との相違や実行できない状態は準備不足として解消し、毎回の再インストールを工程に含めません。Go・task だけで、Node.js、Rust、.NET SDK、WebView など採用構成に必要な依存までそろったとは扱いません。

GitHub Actions の CI ランナーは開発ホストと別の環境です。CI では採用版の Go・task と構成固有の依存を明示的に用意し、ローカルと共通のタスクでビルド・検査します。配布先の端末や Caddy ホストには、開発用であるという理由だけで Go・task を要求しません。[Task 公式ドキュメント：導入と CI での利用](https://taskfile.dev/docs/installation)を参照します。

#### 12.3.6. hooks の準備と起動

hooks の初期作成に必要な最小の Go モジュール・ツール・Taskfile は、通常は工程19〜21の準備として作成・検証します。必要な事前実証では[開発の手順指針の環境準備](development-workflow.md#36-リポジトリと開発環境の準備)に従って最小限を先に準備し、後続工程で再利用します。製品 SDK 導入後の工程22で各構成のタスクを追加します。毎回のフックでツールを再ビルド・依存取得する前提にはせず、起動時間・タイムアウト・更新時の再ビルドを検証し、Go のソースと実行する版を対応付けます。

フック実行は準備済みの Go 実行ファイルを直接起動する形を基本案とし、Taskfile は準備・更新・検証の入口にします。フックの標準出力に通常の Task ログを混ぜません。task を経由する別案を使う場合は、出力と終了コードが保たれることを対象版で検証します。Task の終了コードの引き継ぎは、[CLI の `--exit-code` の説明](https://taskfile.dev/docs/reference/cli)も確認します。配置例・タスク定義・実行例は手順書の執筆時に作成します。

## 13. 家庭内 LAN の HTTPS と共通 CA

### 13.1. 接続と信頼の基本方針

Web アプリは、家庭内 LAN の別端末から `https://<CaddyホストのIPアドレス>:<ポート>/` で利用できる構成にします。「仮 SSL 証明書」は、HTTPS に使用する TLS 証明書として具体化します。

HTTPS には証明書が必要です。Caddy の Local HTTPS では内部 CA が証明書を発行し、Caddy が管理する証明書の更新も行います。家庭内 LAN の基本構成ではこの機能を使い、手動でのサーバー証明書の作成・配置・更新を省く方針とします。[Caddy 公式ドキュメント：Automatic HTTPS](https://caddyserver.com/docs/automatic-https#local-https)

共通 Caddy の内部 CA を、家庭内 LAN 用の共通のプライベート CA（証明書を発行する認証局）として複数アプリで利用します。Caddy が通常作成するルート CA と中間 CA を使い、設定例では `tls internal` などにより内部 CA を使う意図を明示します。[Caddy 公式ドキュメント：内部 CA の指定](https://caddyserver.com/docs/caddyfile/directives/tls#internal)

利用端末には、共通 CA のルート証明書を、利用する OS・ブラウザーなどの信頼ストアへ初回に登録します。同じ CA を継続して利用する間は、アプリを追加するたびに CA を登録し直す運用を避けます。CA の更新・切り替え時や、独自の信頼ストアを持つクライアントは、追加の対応が必要かを確認します。CA を信頼の起点としてサーバー証明書の連鎖を検証する考え方は、[RFC 5280 の証明書パス検証](https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1)を参照します。

Caddy ホスト側での自動的な信頼登録と、LAN 内の利用端末の信頼登録は別に確認します。他の端末にもルート証明書を登録する必要があります。サービスやコンテナーで動かす場合の権限・信頼ストアの違いも、該当する手順で説明します。[Caddy 公式ドキュメント：別端末での信頼登録](https://caddyserver.com/docs/running#local-https-with-systemd)

IP アドレスでアクセスするため、サーバー証明書の SAN（接続先を表す項目）に、対象の IP アドレスを IP アドレスとして含めます。IP の照合では証明書の IP アドレス欄が使われます。[Go 公式ドキュメント：証明書と接続先の照合](https://pkg.go.dev/crypto/x509#Certificate.VerifyHostname)

### 13.2. 手順書で具体化する範囲

- 共通 CA を保持する Caddy のデータディレクトリ、初期作成、バックアップ・復元、更新・切り替えの手順を定めます。
- 利用端末へ配る CA 証明書と、証明書の発行に使う CA の秘密鍵を区別します。CA の秘密鍵は管理場所で保護し、各アプリ・利用端末・リリース成果物へ配布しない方針です。
- HTTPS の終端を担う共通 Caddy が、サーバー証明書と秘密鍵を管理します。Go バックエンド側での証明書の手動管理が必要になる構成は、採用時に理由と手順を追加します。
- 証明書の自動発行・更新の確認、IP アドレス変更時の設定と証明書、更新失敗・期限切れ・CA 切り替え時の対応を記述します。
- Caddy の待ち受け IP・ポート、各アプリへの振り分け、家庭内 LAN からの接続、OS のファイアウォール設定を説明します。
- React／Vue／Svelte のいずれでも、ブラウザーからの API 接続を HTTPS 環境で確認する手順を用意します。
- 配布する Web アプリの成果物と、配備先に固有の IP・証明書・秘密鍵を分けます。機密情報はリポジトリや共通の CI 成果物へ含めない方針です。
- 人の評価では、別端末から IP アドレスで接続し、証明書警告なく画面表示と API 操作が行えることを確認します。アプリを追加した場合にも、共通 CA の再登録が必要になっていないことを確認します。

### 13.3. 共通 Caddy の配置とホスト別の手順

家庭内 LAN 共通の Caddy を1台置き、複数の Web アプリへの入口にします。Caddy で HTTPS を終端し、フロントエンドの配信と Go バックエンドへの転送を行う構成を基本案にします。静的ファイルを配信する場合は `file_server`、バックエンドへ転送する場合は `reverse_proxy` の設定を扱います。[静的ファイル配信](https://caddyserver.com/docs/caddyfile/directives/file_server)、[リバースプロキシ](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

| Caddy ホスト | 手順書で扱う内容 |
| --- | --- |
| Windows 11 amd64 | 導入、設定、サービスとしての起動・停止・再起動、実行アカウント、データの保存先、ファイアウォール、CA の取り出しと信頼登録 |
| Ubuntu 24.04 LTS amd64 | amd64 向けの導入、設定、サービス管理、実行ユーザー、データの保存先と権限、ファイアウォール、CA の取り出しと信頼登録 |
| Ubuntu 24.04 LTS arm64 | arm64 向けの導入と依存関係の確認、設定・サービス・データ・権限・接続の確認。amd64 と分けて確認結果を記録する |

- 各ホストで Caddy の実行アカウントとデータ保存先を固定し、設定の再読み込みやサービス再起動で同じ CA を継続利用する手順を示します。Caddy のデータには証明書・秘密鍵などが含まれ、永続化が必要です。[Caddy 公式ドキュメント：データディレクトリ](https://caddyserver.com/docs/conventions#data-directory)
- アプリ追加時は、共通 Caddy のルーティングと必要な配信・転送先を追加し、同じ内部 CA を利用します。アプリごとに別の Caddy・CA を作る手順を基本フローへ混ぜません。
- Go バックエンドが Caddy と同一ホストの場合は、ループバックで接続する構成を基本案とします。別ホストの場合は、Caddy から Go への経路と暗号化の要否を設計時に決めます。利用端末から Caddy までの HTTPS と、転送先への接続を分けて説明します。
- 再起動・復元後とアプリ追加後にも、CA の識別情報と端末からの接続を確認します。証明書の自動管理を使う場合も、データの保持とルート CA の信頼登録を運用手順に含めます。

Caddy の具体的な版、インストール・サービス管理方法、アプリの振り分けをポート・パスのどちらで行うか、フロントエンド配信方式、固定 IP・DHCP 予約、具体的なブラウザーは、Web 向け補足の執筆前に決めます。3ケースの手順の記載と、各ケースの実践検証状況は分けて管理します。

## 14. 作成と品質確認の進め方

この節は手順書自体の作成工程です。アプリケーションを開発する順序は、[開発の手順指針](development-workflow.md)で別に定めます。

### 手順書の作成工程

1. [想定アプリケーション](example-application.md)の確定事項と残件を確認し、具体プロンプトに必要な題材の前提を本編の執筆前にそろえる。
2. この作成方針と開発の手順指針を基に、新規作成の共通工程と各工程の成果物・承認・完了条件を設計する。
3. 質問を収束させる方法、仕様の記述形式、ひな型を具体化する。
4. Codex を主とする共通手順と、`AGENTS.md` の作成・更新、hooks の作成・検証とルールの再確認・検査、テスト仕様・テストコード・手動評価 `.xlsx` の作成・レビュー、参考・詳細資料を執筆する。各工程に汎用プロンプトと、メモ管理アプリを作るための具体プロンプトを対で用意する。
5. 最初の題材に必要な Go＋Wails v2・デスクトップ向けの補足、人による評価・不具合修正・対象環境別の CI リリース手順を具体化する。
6. Go＋Wails v2 のメモ管理アプリを Windows 11 amd64 向けに、掲載した具体プロンプトを実際に Codex へ入力しながら作成・正式リリースする。Ubuntu 対応を選ぶ場合は、その環境も検証対象に加える。
7. 質問の発散、説明不足、矛盾、操作ミスの原因を記録し、手順書とプロンプトを修正して必要な範囲を再確認する。
8. 確認した共通手順を基に、残りのデスクトップ構成、Web・CLI、家庭内 LAN の HTTPS・共通 CA、Claude Code への補足を整備する。各資料の執筆・レビュー・実践検証の状況を分けて記録する。
9. 品質確認の結果を人が確認し、既存アプリケーションの改修版へ進むか判断する。

### 文書レビューの観点

#### 工程・仕様・承認

- 各工程の入力・成果物・完了条件・戻り先に不足がない。
- 仕様、タスク、自動テスト、人の評価項目の対応が分かる。
- 要求仕様・各種ドキュメント・単体テスト要件・E2E 仕様それぞれの AI レビューとユーザー承認、NG 時の戻り先がある。
- 関連する質問のグループ化、仮置きの確認、質問の終了条件が説明されている。
- `AGENTS.md` の初期作成後も、仕様・設計・実装・リリースに合わせた見直しと、更新後の再読・適用確認の手順がある。
- AI に依頼する各工程に、対応する汎用・具体プロンプトがあり、メモ管理アプリの工程間で入力・成果物・ファイル名・決定事項がつながっている。プロンプトの正本と本文の転載が一致している。
- 不要な設計書、意味が変わらない修正の再承認、差分のない AGENTS.md 更新、編集ごとの全検査、空コミットを要求していない。

#### 作業単位・中断再開

- 大きな工程を30〜60分の作業単位へ分け、確認・保存・再開準備を時間へ含めている。待ち時間を別に記録し、未完了を完了扱いにしない。
- 中断記録から、同じ会話・新しい会話・圧縮後のいずれでも作業先・差分・指示・承認・次の操作を再確認できる。
- 記録は変更分を中心とし、変わらない参照・承認を毎回再記入しない。当日の作業一覧が指定された場合は、その範囲内で継続できる。
- 作業単位の完了と工程全体の承認・完了を区別し、人が待機し続ける時間も当日の枠へ含める。
- レビュー対象とテスト結果の対象版を特定し、再開後の変更へ無条件に成功結果を引き継がない。
- タグ・PR・公開などの実行済み状態を照合して再開し、中断した手動テストは前提条件を復元してから実施する。
- 各工程の `/clear`・`/compact` の使用条件と操作主体、サブエージェントの起動・入力・結果回収・中断時の扱いがある。

#### 環境・ツール・テスト

- Git の初期履歴・ブランチ・リモート、開発ツールと依存関係、標準雛形の起動・ビルド、テスト検出・フォーマッター・リンターの準備を追える。
- 開発ホストの Go・task の前提確認、Go 製の支援ツール、共通の Taskfile、CI 側の環境準備が対応し、Windows の日本語環境で実行結果と生成物を確認できる。
- 設計・自動化の成立を左右する実証は承認前に行い、準備を後続工程で再利用できる。Taskfile の実行順序・対象モジュール・更新条件、hooks の拒否形式、Excel の生成元と環境別評価、必要な性能要求の判定に不足がない。
- テストを実装より先に作る段階の期待する失敗と、実装後・RC 前に成功が必須の検査を区別している。
- 全コードの先行一括作成を強制せず、機能単位のテスト・レビュー・実装・確認を反復できる。保存・UI 連携などの境界に検証の漏れがない。
- 手動評価 `.xlsx` の14列、テスト環境と実施環境の違い、版ごとの結果保存、要求 ID から結果までの追跡が説明されている。
- 実装ルールの再確認、hooks による検査・停止、変更後と CI の検査の役割が明確である。

#### 評価・リリース・文書の整合

- RC 評価の NG から修正・再評価を経て、正式リリースへ進む流れを追える。
- 不具合・修正内容レポートのユーザーレビュー、必要なテストだけの追加、ユーザーによるタグ送信・PR・マージ、タグ CI の役割を追える。
- CI の公開しない早期実行と正式版の公開前確認があり、確認済みの同じ成果物を配布する。配布物の導入・利用・復旧と、完了時の記録・ブランチ整理を説明している。
- 技術構成、対象 OS・CPU、依存関係、CI の成果物、人の評価環境が対応している。
- Web 向けの手順では、共通 Caddy、IP アドレスによる HTTPS、証明書の自動管理、端末の CA 信頼登録、3ケースのホスト手順を説明している。
- 本編、補足、テンプレート、例に矛盾がなく、リンク先が存在する。

### 実践検証で残す記録

実践検証では、使用した手順書の版・環境・ツール、実際に入力したプロンプトと追加指示、`AGENTS.md` の更新理由と差分、質問の回数と追加理由、関連機能の共通ルールと例外、手順書外の補足が必要だった箇所、CI の結果、RC 評価結果、配布した正式版を記録します。実際の不具合が出なかった場合も、不具合修正の手順を検証できたかを記録し、未確認の経路を明示します。

予定・実際の作業時間と待ち時間、分割し直した理由、中断から再開した記録、会話の切り替え・圧縮前後の照合、サブエージェントの起動・回収・終了も記録します。具体的な確認は[作業単位の実践検証](work-session-policy.md#8-実践検証と更新)に従います。

文書レビューでは、要求整理・未実装テスト・長い CI・途中の手動評価・公開操作などの中断場面を、保存状態から次の操作まで順に追います。机上で確認した結果と実機で実行した結果は、レビュー記録と実践検証記録へ分けます。

hooks については、再確認の実績、検査したルール、検出した違反、停止・復帰の結果も記録します。デスクトップアプリでの実践検証で確認した技術構成・OS・CPU と、Web・CLI・他のデスクトップ構成・Claude Code・共通 CA の確認状況を分けて示します。

### 14.1. 検証結果を記録する単位

文書の執筆状況と、手順の動作確認状況を別々に記録します。動作確認には、手順書・プロンプトの版、AI エージェントの利用形態と版、言語・フレームワーク、OS・CPU、確認した工程、結果への参照を付けます。未確認の組み合わせは未検証として示します。

手順書を修正した場合は、影響した工程と後続の入出力を確認し、必要な範囲を再検証します。文書のリンク確認や内容レビューだけでは、アプリの作成・リリースを実践検証済みとは記録しません。

### 14.2. 既存アプリケーションの改修版へ進む判定

少なくとも、共通本編と Go＋Wails v2 のメモ管理アプリの経路について、次を満たしたことを人が確認します。

1. 必要な手順・プロンプト・テンプレートがそろい、工程を進められない説明不足や矛盾が解消している。
2. 掲載した具体プロンプトによって、要件・仕様から CI・RC 評価・正式リリースまで完了した記録がある。
3. `AGENTS.md` の初期作成・更新・再読、テスト作成前の hooks の作成・検証、仕様承認・テスト作成・タグ CI・手動評価、RC の NG から修正・再評価へ戻る経路を確認している。不具合修正の経路は、実際の不具合または再現用のシナリオで確認する。
4. 定めた評価項目が完了し、未解消の NG がない。配布した正式版と、評価済み RC の対応を追える。
5. 残りの補足資料の執筆状況・未検証範囲・残件が明示され、今回の検証で確認できた範囲が分かる。

Web・CLI・他の技術構成や Ubuntu のすべての組み合わせの実践検証は、初回のメモ管理アプリの検証と分けて計画します。指定された補足資料は引き続き作成対象として管理します。

作業単位の時間、中断・再開、会話の切り替え・圧縮とサブエージェントの運用も、上記の検証記録に含めます。確認できなかった経路は、その理由と残件を明示して人が判定します。
