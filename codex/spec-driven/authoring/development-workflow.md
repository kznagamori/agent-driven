作成日：2026-10-15  
更新日：2026-10-15

## 1. この文書の位置付け

新規アプリケーション開発の工程・担当・成果物・完了条件を定めます。開発工程の詳細はこの文書を正本とし、[作成方針](creation-policy.md)と併せて参照します。実行コマンド、汎用・具体プロンプト、テンプレートは `manual/` に執筆します。

仕様とテスト計画は全体を先にレビュー・承認し、テストコードと製品コードは機能単位で作成・レビュー・実装・確認を反復します。各操作は、開発対象アプリのリポジトリで行います。

工程1〜43は大きな段階を示します。各工程を30〜60分の作業単位へ分け、平日の1〜4時間で中断・再開できる形にします。分割・保存、`/clear`・`/compact`、サブエージェントの扱いは[作業単位・AI コンテキストの方針](work-session-policy.md)に従います。

## 2. 成果物と承認の基本

### 2.1. 仕様・設計・テストの役割

| 成果物 | 記載する内容 |
| --- | --- |
| 簡易なアイデア・整理結果 | 目的、利用者、主要な使い方、今回の対象範囲、制約、確認した推奨案 |
| 要求仕様書 | 作るものの要求、振る舞い、非機能要求、対象環境、受け入れ条件、対象外の範囲、要求 ID |
| 各種ドキュメント | 承認済み要求を具体化した仕様・設計・実装計画。機能、画面、データ、API、構成・依存方向など、アプリに必要な文書を選定する |
| 単体テスト要件仕様書 | 単体テストで必ず確認する事項、禁止事項、対象と境界、正常・異常・境界値の観点、実行方法、完了条件。外部依存の扱いなどのルールも定義する |
| E2E テスト仕様書 | 利用開始から操作結果までの一連の確認。自動・手動を区分し、ID、関連要求、環境、前提、手順、期待結果を記載する |
| テストコード・手動評価ファイル | 承認済みテスト仕様を実行・記録できる形にしたもの。手動評価は `.xlsx` を使用する |
| 不具合・修正内容レポート | 不具合の再現情報、原因調査、修正方針、影響範囲、追加・変更が必要なテスト、確認結果 |

「要求仕様書」はアプリの要求の正本、「単体テスト要件仕様書」はテストの必須事項・禁止事項などの定義書として使い分けます。文書の分割数を固定せず、各文書の役割と参照関係を明示します。

小規模なアプリでは、仕様・設計・実装計画の複数の役割を、一つのファイルの節としてまとめても構いません。記載内容と承認対象を特定できれば、不要な API 設計書などを別途作りません。レビュー結果と承認記録も、成果物への参照と判断を含む共通の記録にまとめられます。

文書をまとめる場合も、各要求の達成条件、機能間の契約、データの保存と失敗時の振る舞い、対応環境、配布方法は追えるようにします。実装計画には、要求 ID、依存する作業、先に作るテスト、確認可能な小さな機能の単位、完了条件を持たせます。性能・安全性・復旧などの非機能要求は、そのアプリで必要なものを選び、測定・評価方法を定めます。

### 2.2. レビューと承認

AI は成果物を作成した後、入力の承認済み文書と照合してレビューします。レビューで見つけた問題を修正し、未解消事項と判断が必要な事項を示します。AI 自身のレビューで、ユーザー承認を代替しません。

レビュー・承認の対象は、保存済みのファイルと版を特定します。未コミットの変更を扱う場合も、その変更範囲を含めて対象を決め、確認中に対象を変えません。変更後は影響する部分を再確認し、以前のレビューや承認を変更後の全体へ無条件に引き継ぎません。

ユーザーの承認が必要な節目は、要求仕様書、各種ドキュメント、単体テスト要件仕様書、E2E テスト仕様書です。NG の場合はその作成・レビューへ戻り、修正後に再承認を受けます。承認したファイルと版、日付、判断を記録し、未承認の重要事項を AI が独断で確定しません。

承認後に要求の意味、受け入れ条件、外部との契約、設計上の制約、テストの期待結果を変える場合は、影響する文書を先に更新し、変更部分の再承認を受けてから後続成果物へ反映します。意味が変わらない誤字・リンク・体裁の修正や、承認済みの設計の範囲内での実装詳細は、AI のレビューと変更記録で扱い、承認を毎回やり直しません。指示ファイルや hooks の更新によって、承認済み仕様を変更しないようにします。

### 3.6. リポジトリと開発環境の準備

#### 3.6.1. リポジトリと共通ツール

工程2では、作業先・既存ファイル・Git の状態を確認します。新規リポジトリでは、指示・説明文などの初期コミットを `main` に置き、共通の履歴から `develop` を作る流れを示します。既存の履歴は作り直しません。GitHub 側のリポジトリ、リモート、コミットの作者設定、ユーザーが push・PR・タグ操作できる認証を確認し、認証情報そのものを文書へ保存しません。AI がコミットしても、ユーザーが送信・PR・マージを行う役割分担を保ちます。

Go と task（go-task）は開発ホストにインストール済みとし、工程2で `go version`・`task --version` と実行可否を確認します。以後の自作支援ツールは Go、共通の実行入口はルートの `Taskfile.yml` とします。適用範囲、版管理、CI との対応は[開発支援ツールと task の方針](creation-policy.md#123-開発支援ツールと-task)を正本とします。SDK や製品構成の依存は別に準備します。

#### 3.6.2. 重要な技術条件の事前実証

工程8〜17では、採用する技術・対象環境・テスト手段の対応状況を公式資料と環境情報から調べます。資料だけでは判断できず、設計の成立やテストの実行可否を左右する点は、対応する設計・テスト仕様の承認前に、小さな実証で確認します。例えばデスクトップの起動・UI 連携・自動化手段や、必須性能の実現性を対象にします。公式資料で確認できる事項まで一律に試作しません。

事前実証が必要な場合は、対象・目的・判定条件・30〜60分の範囲を記録し、隔離した検証先で行います。コードを書く前に必要最小限のルール・Go ツール・Taskfile と事前 hooks を準備・確認します。hooks 自身の初期作成は第4節の準備方法を使います。検証に必要な SDK・標準雛形だけを先に用意し、製品機能の実装や製品のテスト完了とは区別します。採用した環境・設定・結果は工程19〜22で再利用・更新し、同じ準備を作り直しません。確認できない重要条件を成立した前提で承認へ進めず、理由付き代案や対象範囲の見直しを示します。

特定 CI ランナー上での成立確認が必要なら、公開を伴わない最小の CI 検証も承認前に行い、工程29で再利用・拡張します。ユーザーが担当する送信・実行操作は保ち、試作用の追加リリースタグは要求しません。ローカルでの成功だけで、その CI ランナーでの実行可否まで確認したとは扱いません。

独自のフィジビリティチェックや性能計測が必要な場合は、Go の検証・計測ツールを使い、対象の要求・採用版・入力・環境・判定基準・結果を残します。対象技術の検証に必要な最小のサンプルは、その技術の言語・SDK を使用できます。Go による代用品だけで、Wails・Tauri・WPF などの実現性を確認したとは扱いません。通常の最小準備は工程19〜21、製品構成の環境とタスクは工程22、実際の CI の全経路は工程29で確認します。ツールの作成・レビュー・動作確認も30〜60分の作業単位へ分けます。

#### 3.6.3. アプリの開発環境と標準雛形

工程22では、SDK・言語・Node.js 等の必要なツール、ネイティブ依存、採用版、パッケージ管理と ロックファイルをそろえます。承認済み構成でフレームワークの標準雛形を生成し、起動・ビルド、テスト用の検出確認、フォーマッター・リンターを確認します。検出確認用の一時テストは、要求の検証実績に数えません。`README.md` にセットアップと正確なコマンドを、設定ファイルに共有できる値を残し、機械固有値・生成物の除外を設定します。生成したファイルも既存の指示を上書きしていないか確認します。

雛形生成は、承認済み仕様の製品機能を実装する前の準備として扱い、hooks を適用します。Go＋Wails v2 の場合は Go 側だけでなく、フロントエンド・生成される連携コード・配布用ビルドも確認対象です。WebView2 や Linux 側のネイティブ依存、Ubuntu 24.04 のビルド条件など、採用版の前提を補足資料へ記載します。[Wails v2 の導入資料](https://wails.io/docs/gettingstarted/installation/)、[ビルド資料](https://wails.io/docs/gettingstarted/building/)（確認日：2026-10-15）。

#### 3.6.4. hooks の検証時期

hooks のルール再読・変更前の検査は工程21までに確認し、ツールチェーンに依存する変更後の検査は導入後に追加確認します。存在しないビルド・リンターコマンドを hooks から必須実行して、環境準備が進められなくなる状態を避けます。工程30までに必要な検査を機能させ、製品機能の実装へ進みます。

### 3.7. 作業時間・中断再開・AI の利用

工程の中を、一つの関連テーマ・要求・検証対象などの作業単位へ分けます。開始時に目的・入力・成果物・確認・保存先・時間の見込みを定め、確認と再開用の記録を含めて30〜60分に収めるよう計画します。60分を超える見込みなら分割し、作業途中でも保存・中断できる状態を維持します。

工程全体のユーザー承認と完了条件は保ちます。途中成果・未実行のテスト・未回収のレビュー結果を保存しても、全体が承認・検証済みになった扱いにはしません。CI などの長い処理は実行 ID と状態を保存し、開始と結果確認を別の作業単位へ分けます。

作業単位の状態と工程全体の承認・完了は別に記録します。当日の時間枠と作業一覧が指定されていれば、単位ごとの保存後、その範囲内で次の作業へ進めます。短い作業ごとに同じ承認・環境情報を再記入することや、新しい承認を求めることは必須にしません。具体的な省力化と再開時の照合は、[中断・再開の記録](work-session-policy.md#3-中断と再開の記録)に従います。

各作業単位に、同じ会話を継続するか、保存後に `/clear`・`/compact` を使うか、サブエージェントを起動するかを記載します。工程1〜43と不具合修正ループを網羅した[分割・AI 利用の対応表](work-session-policy.md#6-開発工程ごとの分割と-ai-の利用案)を、本編・汎用プロンプト・具体プロンプトへ反映します。

## 4. AGENTS.md と hooks を組み込む条件

`AGENTS.md` は工程2で初期作成し、要求・設計・テスト仕様の承認後、hooks・CI 導入後、不具合修正で規則が変わる場合に更新の要否を確認します。変わる規則・参照先がない節目では更新不要と記録し、差分を作ること自体を目的にしません。既存指示の確認、差分更新、リンク・コマンドの確認、明示的な再読・適用確認は、[指示ファイルの更新方針](creation-policy.md#101-agentsmd-の初期作成後の更新)に従います。

hooks は製品コードだけでなく、単体テスト・E2E 自動テストの作成にも適用します。そのため、最初の製品の雛形・テストコード作成より前の工程19〜21で整備します。第3.6節の事前実証にコードが必要な場合は、実証に必要な事前検査だけを先に整備し、工程19〜21で承認済みルールへの適合を確認します。hooks 自身と最小の検査環境の作成は準備作業として区別し、この準備中は適用ルールを明示的に再読して差分をレビューします。検証後は hooks 自身の変更も適用範囲に含め、無効化・設定変更を記録します。

作成する設定と Go の検査ツールには、対象イベント・ツール・ファイル、ルールの正本、読んだ版の識別方法、検査内容、拒否条件、ログ、停止からの復帰方法を定めます。Taskfile から準備・検証できるようにし、フックからの起動時間・タイムアウトと更新時の再ビルドも確認します。タスク開始・再開時の再読と、変更前・変更後の検査を組み合わせます。ツールごとの出力とタイミングの制約は、[hooks の設計・検証条件](creation-policy.md#113-hooks-を設計検証する際の条件)に従います。

task・CI の検査の非ゼロ終了と、AI エージェントのフックによる拒否は同一視しません。フック用の Go プログラムは標準入力のイベントを読み、成功・違反・検査不能を区別し、対象イベントが対応する拒否 JSON または終了コードへ変換します。Taskfile はビルド・検証の入口とし、フック実行は準備済みの Go 実行ファイルを直接起動する形を基本案にします。標準出力へ Task のログやビルドの表示を混ぜず、診断は標準エラーへ出します。呼び出し側が必要とする形式・終了コードを保ち、単なる異常終了を「変更を止めた証拠」にしません。[Go ツールからの呼び出し方針](creation-policy.md#123-開発支援ツールと-task)も参照します。

編集のたびに全資料の再注入や全テストを必須にせず、適用ルールの全文はタスク開始・再開・ルール更新時に再読し、変更の直前は参照した版と対象に応じた検査を行います。変更後は影響範囲の検査を実行し、全体の必須検査は機能の完了時・RC 前・CI で確認します。hooks の存在や再読ログだけで、意味上のすべての違反を防止できたとは判定しません。[OpenAI 公式ドキュメント：hooks の対象範囲と例外](https://learn.chatgpt.com/docs/hooks#tool-coverage)も参照します。

動作検証では、ルールを表示できたことと、そのルールに反する変更を実際に止めたことを分けて記録します。検出対象の違反を含む変更が止まり、ルールの再読・修正後に正常に進むことまで確認します。検証用の違反は隔離した作業対象で扱い、製品コードへ残しません。

テストを先に作る段階の想定内の未実装失敗と、ルール違反・テストの欠陥を区別します。hooks の検査範囲と工程ごとの合格条件を定め、製品未実装のテストがあることだけを理由に、テスト作成自体が進められなくなる構成を避けます。必須のルール検査の失敗は解消してから進みます。

## 5. テストを実装より先に作る際の扱い

単体・E2E 自動テストは承認済み仕様から作り、対応する機能の実装より先にレビューします。アプリ全体のテストコードを一括で完成させることは前提にしません。工程23〜26で実行基盤と最初の機能のテストを作り、工程31では後続機能についても同じ順序を反復します。テスト仕様は全体の確認項目を持ち、未作成のテストと対応タスクを管理します。

実装に必要な公開インターフェース・データ契約は設計で定めます。テストを実行するためだけの最小の宣言・未実装の入口を置く場合は、機能実装と区別してレビューします。生成コードや実 UI に依存する E2E の詳細は、その境界が確認できた時点で仕上げます。設計を変えずにセレクターなどを同期する修正は、その都度のレビューで扱います。テストを書いた都合だけで要求や契約・期待結果を変更しません。

製品未実装の段階では、期待する失敗や未実行のケースがあり得ます。テスト環境・構文・テストデータの不備と、未実装機能による失敗を区別し、実行できた範囲と失敗理由を記録します。実行可能な単体テストは実装前の失敗と実装後の成功を確認し、未実行のケースは検証済みに数えません。アプリ全体の全件成功をこの段階の条件にしません。テストを通すために期待結果を弱めたり、未実装ケースを恒久的に除外したりしません。

実装中は、変更単位で関係する単体テストを実行し、主要な利用の流れが起動から結果確認まで実行可能になった時点で、対応する E2E 自動テストの実行を開始します。「ある程度の規模」は、この実行可能な機能のまとまりで判断します。実装が進んだ後は関連する回帰テストも実行します。RC タグ前には指定した実行環境ですべての必須自動テストを成功させ、タグ CI では CI 実行対象の必須検査をすべて成功させます。

UI と Go の連携、保存処理など、単体テストだけでは確かめられない境界も検証方法を割り当てます。E2E で十分に確認できない場合は結合テストを追加し、必要な理由と実行先を同じテスト仕様・対応表に記載します。すべての機能に別の結合テスト仕様書や重複テストを要求しません。

CI の作成時点も、製品未実装の失敗と CI 設定・環境の不備を分けて確認します。初期の構成確認だけで CI 検証済みとせず、実装後にテスト成功・成果物作成・取得までを確認します。

製品・フロントエンド・Go 支援ツールなど、検査対象と実行ディレクトリ・モジュール・タスクを対応付けます。複数の Go モジュールを採用した場合は必要な各モジュールを検査し、一つのディレクトリでの成功だけで全体完了にしません。支援ツールは、ケースの欠落・結果の上書き・誤った変更許可など、開発結果を損なう重要な振る舞いを小さな入力で確認します。ツールごとの別仕様書や同じ処理の重複テストは一律に追加しません。

## 6. E2E 手動テスト評価ファイル

### 6.1. 必須の列

以下の14列を、この順番で記載します。

| 順番 | 列名 | 記入内容 |
| --- | --- | --- |
| 1 | ID | E2E テスト仕様書と同じ手動テスト ID |
| 2 | テストグループ | 関連機能・利用の流れごとの分類 |
| 3 | テスト環境 | 仕様で予定した OS・CPU・必要条件など |
| 4 | 優先度 | テスト仕様書で定めた優先度 |
| 5 | テスト概要 | 何を確認するケースか |
| 6 | 前提条件 | データ・設定・起動状態など |
| 7 | テスト手順 | 実行する操作を順序付きで記載 |
| 8 | テスト確認内容 | 合否を判定できる期待結果 |
| 9 | 関連要求 | 対応する要求仕様書の要求 ID |
| 10 | テスト実施日 | 実際に確認した日 |
| 11 | ソフトウェアバージョン | 評価した RC または正式版の識別子 |
| 12 | 実施環境 | 実際に使用した OS・CPU・依存環境など |
| 13 | 実施者 | 評価を実施した人 |
| 14 | テスト確認結果 | 結果と、NG の場合の不具合レポートへの参照 |

「テスト環境」は予定する条件、「実施環境」は実際の条件として区別します。未実施と成功・失敗を区別し、優先度が低いことだけを理由に必須ケースを省略しません。NG・未実施・保留などの具体的な入力値は、テンプレートの執筆時に定めます。

### 6.2. 作成・レビュー・履歴

#### ケース定義と生成

E2E テスト仕様書を正本とし、評価ファイルだけに新しい仕様を追加しません。仕様書の表または付属の構造化データの一方をケース定義の編集元として決め、Go の生成ツールが同じ定義を読み取るようにします。Markdown と JSON・YAML などで同じケースを手作業により二重管理しません。編集元を含めて工程15〜17のレビュー・承認対象とし、生成時に ID・関連要求・必須項目・手動ケースの件数を照合します。入力形式と表計算ソフトは手順書の執筆時に具体化します。

ケースの追加・修正時は、仕様書、ファイル、要求 ID の対応をそろえます。AI のレビューで、14列の一致、手動ケースの網羅、意図しない重複、手順・期待結果の欠落を確認します。表示の切れ、折り返し、入力箇所の識別、保存・再表示も確認対象です。

生成処理は Go で作り、task から実行します。入力形式・出力先・生成元の版を明示し、ライブラリと依存を固定します。日本語のケースを含めて生成後のファイルを利用予定の表計算ソフトで確認し、Excel 本体やマクロでの生成を必須にしません。新規ひな型の生成と記入済み結果の保存を分け、既存結果の上書きを防ぎます。

#### 評価結果の保存と環境別の識別

ユーザーが実施結果を記入する前のファイルはひな型として保存し、各 RC・評価回の結果は別に残します。新しい RC の結果で以前の評価結果を上書きしません。結果ファイルと評価対象の CI 実行・成果物への参照を、評価記録で対応付けます。

同じケースを複数の OS・CPU で評価する場合は、ケース ID を共通に保ち、予定環境ごとに行・シート・ファイルのいずれかを分けます。「評価回・対象成果物・予定環境・ケース ID」で結果を識別し、予定環境と実施環境を照合します。14列は追加・変更せず、評価回・生成元の版・成果物の参照はファイル単位の評価記録などに置きます。同一環境内の重複と、別環境での同じケースの実施を区別します。

#### 中断と再開

手動テストの途中で中断したケースは、成功と区別して状態と残りの確認を保存します。再開時に対象版・環境・データ・前提条件を確認し、途中の状態を復元できなければそのケースを最初から実施します。完了したケースは、変更の影響がなければその結果を保持します。実行結果の記録だけを根拠に、未確認の手順を飛ばして成功へ変更しません。

今回定めるのは作成方針です。実際の `.xlsx` ひな型、記入例、レビュー用の確認手順は、手順書の執筆時に作成します。

## 7. トレーサビリティ

要求 ID を要求仕様書の作成時に付け、その後の仕様・設計、単体テスト、E2E 自動・手動テスト、結果、不具合レポートまで対応を追えるようにします。ID は一意にし、削除した ID を別の意味で再利用しません。複数の要求に対応するテストは、関連する ID をすべて記載します。

命名の例は `REQ-001`、`UT-001`、`E2E-A-001`、`E2E-M-001`、`BUG-001` とします。これは書式の案であり、正式な書式と管理方法はテンプレート作成時に定めます。

対応表では、少なくとも「要求 → 仕様・設計 → 必要なテスト → 実行結果」を確認します。すべての要求に単体・自動 E2E・手動 E2E の全種類を機械的に課さず、検証方法と採用理由を要求ごとに明示します。テスト不要・対象外の判断も、未対応の要求と区別して記録します。

## 8. 不具合がある場合の修正ループ

| 順番 | 担当 | 作業・条件 |
| --- | --- | --- |
| 1 | ユーザー | 評価結果・不具合情報を渡し、AI に不具合・修正内容レポートの作成を依頼する |
| 2 | AI | 再現、期待結果と実際の結果、対象 RC・テスト ID・環境、原因、修正案、影響範囲、必要なテスト変更をまとめる。未確認の原因は仮説と区別する |
| 3 | ユーザー | レポートをレビューする。NG は調査・レポート修正へ戻る。確認した方針を記録してから修正へ進む |
| 4 | AI | 承認済みの要求・設計・テストの期待結果を変える場合は、先に関係する文書を更新して再承認を受ける。必要なら `AGENTS.md`・実装ルール・hooks も更新・再確認する |
| 5 | AI | 必要な場合だけ、単体・E2E 自動・E2E 手動の仕様とテストを追加・修正し、レビューする。既存テストで十分な場合は、その理由を記録する |
| 6 | AI | レポートに従って修正し、単体・E2E 自動テストを実行する。修正箇所と影響範囲の回帰確認を行い、差分・結果をレビューしてコミットする |
| 7 | ユーザー | 修正した `develop` のコミットに、新しい RC タグを付けて GitHub へ送信する |
| 8 | CI | 新しい RC をビルド・自動テストし、成果物を作成する。失敗時は原因を修正して再度 RC 作成へ戻る |
| 9 | ユーザー | 新しい RC 成果物で手動 E2E を再実施し、結果を保存する。修正確認だけでなく影響する既存ケースも再評価する |

必須評価が完了し、未解消の NG がなくなるまで繰り返します。再評価の範囲は変更の影響から定め、同じ内容を確認していない以前の結果を無条件に引き継ぎません。すべての不具合についてテストを3種類追加する運用にはしません。

CI の一時的な通信障害など、ソース・依存関係・ビルド条件を変えずに解消できる失敗は、同じタグの CI を再実行して構いません。コード・設定・ビルド条件を修正した場合は新しいコミットと RC タグを使います。いずれも採用した CI 実行と成果物を特定し、以前の評価済みファイルと混同しません。

処理の中断と、再現した製品不具合は区別します。中断だけで新しい不具合レポートや RC を必須にせず、実行結果・成果物・入力条件を調べて再試行の要否を決めます。再実行で採用する成果物が変わった場合は、以前の手動評価との対応と必要な再評価を確認します。[GitHub 公式ドキュメント：ワークフロー・ジョブの再実行](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)も参照します。

## 9. タグ CI と正式版への移行条件

### 9.1. RC と正式版の契機

| 対象 | ユーザーの操作 | CI の必須処理 | 人による次の確認 |
| --- | --- | --- | --- |
| RC | `develop` の対象コミットへ RC タグを付け、GitHub に送信する | ビルド、単体テスト、CI で実行可能な必須 E2E 自動テスト、RC 成果物作成 | その RC 成果物で手動 E2E を実施する |
| 正式版 | PR・マージ後の `main` の対象コミットへ正式版タグを付け、GitHub に送信する | ビルド、自動テスト、未公開の正式版成果物作成、RC との対応の記録 | 正式版の差分・起動・主要操作などを確認し、同じ成果物を公開・配布する |

タグ名は `v1.0.0-rc.1`、`v1.0.0` などを例とし、正式な命名規則は CI 手順の執筆時に確定します。タグは対象コミットを指すため、CI ではタグの種類に加え、対象コミットがリリース対象ブランチの適切な状態かを確認する方法を定めます。

ローカルでタグを作っただけでは GitHub の処理は始まりません。手順書では GitHub への送信と実行確認までを記載します。タグの `push` を契機とする設定は、[GitHub 公式ドキュメント：特定タグの送信による実行](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#running-your-workflow-only-when-a-push-of-specific-tags-occurs)に従います（確認日：2026-10-15）。

`main` へのマージと、正式版タグによるリリース処理を区別します。ブランチ更新・PR 時の追加 CI を導入する場合も、必須のタグ CI を置き換えません。配布済み・評価済みタグを別のコミットへ付け替えず、修正時は新しい版で識別します。

タグ送信・PR・マージ・公開の途中で中断した場合は、リモートのタグとコミット、CI、PR、公開状態を確認してから再開します。完了していれば次の確認から進み、不明なまま同じ操作を繰り返しません。ユーザーの操作に必要な調査・記録は AI が支援します。[再開時の照合](work-session-policy.md#33-再開する順序)に従います。

正式版の成果物作成と公開は分けます。配布前確認が完了するまでは Actions の成果物、または GitHub Release の draft で保持し、確認したファイルをそのまま公開します。RC は候補版として明示します。公開・保存する場所、取得権限、保存期間、成果物の識別値を定め、GitHub Release を公開する操作はユーザーが担当します。[GitHub 公式ドキュメント：リリースの下書きと公開](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)（確認日：2026-10-15）。

### 9.2. CI で確認する範囲

CI は最終 RC タグで初めて動かす運用にせず、工程29で公開を伴わない実行経路を用意します。手動実行または開発ブランチの検証用実行などから、実際の CI ランナー上で雛形のビルド、テストの検出・実行、成果物の取得を確かめます。方式は手順書で一つを基本例として選び、タグ CI と同じビルド・テスト処理を共用します。追加のリリース用タグや、すべての変更への必須 PR は、この確認のためには増やしません。

CI ランナーに Go・task が導入済みとは仮定せず、採用版と構成固有の SDK・依存を CI で用意します。ローカルと同じ Taskfile のビルド・検査タスクを使い、タグ判定・成果物の保存・公開制御など GitHub 固有の処理は workflow で定義します。支援ツールを変更した際は、必要な再ビルドを行い、古い実行ファイルの検査結果を使わないようにします。

Taskfile の共通処理は[実行順序と検査範囲の方針](creation-policy.md#123-開発支援ツールと-task)に従い、コード生成・ビルド・テストの必要な順序を守ります。必須検査を Task の更新判定や対象 OS の不一致だけで省略しません。コンパイラー等のビルドキャッシュと、実施していないテストの成功扱いを区別し、同じ検査を workflow に二重実装しないようにします。

CI 実行が失敗した場合は、未実装機能による想定内の失敗か、設定・環境の不備かを記録します。タグ CI ではビルドとすべての必須検査の成功を成果物の評価・公開条件とし、`continue-on-error`、意図しない skip、テストが0件の状態で合格扱いにしません。診断用ログと、評価・配布できる成果物は区別します。

対象 OS・CPU、ビルド環境、単体・E2E 自動テストの実行環境、成果物、人の実施環境を対応表にします。CI ランナーの OS と、実際に動作保証・評価する OS を区別します。利用可能な CI ランナーと仕様は、[GitHub の公式一覧](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)を執筆時に確認します（今回の確認日：2026-10-15）。

デスクトップのネイティブ画面を含む E2E は、採用する自動化手段・CI ランナーで実行できる範囲を事前に検証します。ブラウザー内の UI やバックエンドだけのテストと、配布されたデスクトップアプリ全体の確認を区別します。CI で実行できない確認は手動 E2E などの担当・環境を定め、未実行のまま成功扱いにしません。

### 9.3. 評価後の変更と正式版の確認

RC ごとに、要求・設計・テスト仕様の版、ソースのコミット、依存関係、ビルド条件、CI 実行、成果物、手動結果を保存します。評価後の変更やマージ時の差分が動作に影響する場合は、新しい RC を作成して再評価します。

評価記録などの追記で変更が発生した場合だけ、工程37でコミットします。変更の影響を確認せず、評価済みという理由だけでその後のコード・テスト・設定変更を正式版へ進めないようにします。PR 作成からマージまでの `develop` の追加コミットも確認し、評価対象外の変更が含まれる場合は PR 対象を整理するか、新しい RC で評価します。

正式版は `main` のタグから再ビルドするため、評価済み RC とのソース・依存関係・ビルド条件の対応と、予定したバージョン表記などの差分を確認します。コミット ID がマージによって変わっても、その対応を追えるようにします。正式版成果物で配布前の確認を行い、NG があれば修正・RC 評価へ戻ります。[正式版と RC の対応方針](creation-policy.md#71-rc-の評価結果と正式版を対応付ける)も参照します。

### 9.4. 配布物での評価と配備・復旧

RC 評価と正式版の確認では、開発用起動だけで済ませず、CI が作成した配布物を、対象環境の新しい作業先または評価用の利用状態へ導入します。導入・起動・主要操作・保存後の再起動など、要求で必要とした条件を確認します。開発用 SDK や作業ディレクトリがない利用者環境でも、配布方針で定めたランタイムだけで使用できることを評価します。

| 種類 | 仕様・設計で決め、配布物で確かめる内容 |
| --- | --- |
| デスクトップ | インストーラー／展開形式、必要なランタイム、起動方法、保存先と権限、データの継続利用、削除方法 |
| CLI | 配布形式、配置・起動方法、引数・入出力・終了コード、設定とデータの保存先 |
| Web | フロントエンド・Go バックエンド・Caddy 設定の配置、起動・停止、配備先固有値、IP・CA の準備、別端末からの HTTPS 操作 |

利用者向けの導入・操作説明、既知の制約、データを保持してやり直す方法、配布後に不具合を報告するための版・ログの確認方法を用意します。新規アプリでも保存データがある場合は、評価前のバックアップと復元の方法を定めます。更新・移行・署名などは、採用する配布形態と要求に該当する場合に追加し、すべてのアプリへ一律に課しません。

正式版確認で NG になった場合は、`develop` で修正して RC から再評価し、再度 `main` への PR・マージと新しい正式版タグへ進みます。既に `main` にだけ入った変更があれば先に `develop` との対応を整理します。公開後の問題は、対象成果物の案内・必要な公開停止・復旧と、新しい版での修正を同じ不具合レポートから追えるようにします。

## 11. 手順書執筆時に具体化すること

- 各工程の入力ファイル、成果物、汎用・具体プロンプト、レビューと承認の記録方法。
- 工程内の30〜60分の作業単位、見込み・実際の時間と待ち時間、途中中断の保存、翌日などの再開操作。

- 重要な事前実証の対象・判定条件、最小限の hooks・SDK・CI の前倒しと再利用、実証と製品実装・製品テストを区別する記録。
- Go・task の採用版、Go 製の支援ツールとモジュールの配置、Taskfile の実行順序・検査対象・更新条件、Windows 日本語環境と対応 Ubuntu 環境での確認、CI の準備と共通タスク。
- 要求・設計・テスト仕様のひな型、ID の正式書式、トレーサビリティの管理方法。
- hooks の設定・Go の検査ツール、適用ルールと変更経路、工程別の検査・停止・復帰、作成直後の検証例。

これらは新しい機能要求を増やす質問ではなく、合意済みの工程を実行可能にする執筆上の残件として管理します。題材アプリの仕様・技術の選択が必要な事項は、[想定アプリケーション](example-application.md)の関連テーマにまとめて確認します。
