# 具体プロンプトと実践検証に使う想定アプリケーション

作成日：2026-10-15  
更新日：2026-10-15  
状態：題材・基本機能・主要技術を決定済み。詳細な仕様と具体プロンプトは今後作成する。

## 1. この文書の目的

手順書に掲載する具体プロンプトの題材を、本編の執筆前に決めて記録します。同じ題材を工程を通して使い、実際に Codex へ入力するプロンプトと、その結果として作成する文書・アプリケーションのつながりを保つための文書です。

この文書は手順書作成側の計画です。題材アプリの詳細な要件・仕様は、手順書内でアイデアから整理する過程も含めて示します。

## 2. 利用者との確認で決まった事項

| 項目 | 決定内容 |
| --- | --- |
| アプリの題材 | メモ管理デスクトップアプリ |
| 基本機能 | メモの登録・編集・検索・タグ・保存 |
| 主要な技術構成 | Go＋Wails v2 |
| 開発支援と実行入口 | 自作支援ツールは Go、タスクランナーは task（go-task）。開発ホストは両方の導入済みを前提とする |
| 用途 | 共通本編の具体プロンプトと、初回のデスクトップアプリによる実践検証に使用する |

対象環境は[作成方針](creation-policy.md#12-技術構成と対象環境)に従い、Windows 11 amd64 を基本にします。Ubuntu 24.04 以降の amd64／arm64 を、この題材でも対象に加えるかは未決です。

文書配置用の識別子は `memo-manager` とします。アプリの正式な製品名・配布名は、題材の詳細を整理する際に決めます。

## 3. 本編の執筆前にまとめて確認する事項

次を関連するテーマにまとめ、AI が理由付き推奨案を提示し、人が確認します。基本機能を作成・評価できる範囲に絞り、追加の機能案は初版に必要かを分けて判断します。

| テーマ | 整理する内容 |
| --- | --- |
| 利用方法と初版の範囲 | 誰が何のために使うか、主要な操作の流れ、今回扱う範囲 |
| UI とメモの形式 | Wails v2 で使うフロントエンド、画面の構成、タイトル・本文などの項目、プレーンテキスト等の扱い |
| 登録・編集・保存 | 保存先・保存形式、手動保存／自動保存、入力の検証、保存失敗時の共通の振る舞い |
| 検索・タグ | 検索対象、照合方法、タグの付与・変更、検索との組み合わせ、該当なしの場合 |
| 評価と配布 | 受け入れ条件の観点、配布形式と必要なランタイム、CI の成果物、RC の導入・再起動後の保存確認、人の評価、対応 OS・CPU の範囲 |

詳細を決める際は、[作成方針の質問を収束させる方法](creation-policy.md#6-質問が発散しない仕組み)を適用します。保存方式や UI 技術など、プロンプトを具体化するために必要な選択は、本編の執筆開始前に収束させます。

ここで準備する仕様・設計は、執筆者が一貫した例題を作るための想定です。本編では、簡易なアイデア、要件を確認する際の回答、設計時の選択を段階ごとに示し、その時点で読者が持つ情報を区別します。準備した想定と実際の対話・検証結果が異なった場合は、理由と影響を確認して、題材の記録・プロンプト・成果物の例をそろえて更新します。

## 4. 具体プロンプトを作成する際の扱い

### 4.1. 入力と情報の引き継ぎ

- 最初の入力は、人が用意する簡易なアイデアとして示します。
- 要件・仕様の工程では、関連質問への回答、理由付き推奨案の確認、仕様確定までの流れを示します。
- 各工程で確定した情報と成果物を、次の工程のプロンプトへ引き継ぎます。まだ決まっていない将来の設計を、初期の依頼文へ混ぜません。

### 4.2. 準備と開発工程

- `/init` による初期作成と、要求・設計・テスト仕様の承認後、hooks・CI 導入後の `AGENTS.md` 更新も、操作と具体プロンプトの対象にします。
- [開発の手順指針](development-workflow.md)に合わせて、テスト作成前の hooks の作成・レビュー・動作検証、単体テスト要件仕様と自動・手動 E2E 仕様の承認、テストコードと手動評価 `.xlsx` の作成・レビューを具体化します。
- 初期 Git 履歴・ブランチ・リモート、採用版と依存関係、最小の Wails アプリ雛形の起動・ビルド・テスト環境、公開しない CI の早期実行も工程として示します。hooks の事前検査と、ツール導入後の変更後検査の確認時期を分けます。
- Wails の UI 連携や自動化など設計の成立を左右する未確認点があれば、承認前に小さな実証を行う例を示します。必要最小限の事前 hooks・環境・CI は後続工程で再利用し、試作を製品の実装・テスト成功と混同しません。
- [開発支援ツールの方針](creation-policy.md#123-開発支援ツールと-task)に合わせ、導入済み Go・task の確認、最小の Go ツール・Taskfile の準備、Wails のビルド・テスト用タスクの追加、Go による14列の `.xlsx` 生成を具体化します。独自のフィジビリティチェック・計測が必要な場合も Go を使い、生成・計測の入力と結果を追える例にします。
- テスト仕様の全体承認後、メモの登録・保存など確認可能な小さな単位で、テスト先行作成・レビュー・実装・実行を反復します。最初にすべてのテストコードを完成させる例にはしません。

### 4.3. ID・品質・プロンプトの管理

- 具体例でも同じ要求 ID・テスト ID を使い、14列の手動評価、必要なテストだけを追加する不具合修正、ユーザーの RC／正式版タグ送信・PR・マージへつなげます。
- 実装・テスト・RC 作成・不具合修正・正式リリースまで、同じアプリの文書・ソース・成果物を対象として追えるようにします。
- 汎用プロンプトと具体プロンプトを、同じ目的・制約・完了条件で対応付けます。
- AI の回答例や生成する成果物の想定例と、実際に検証した記録を区別します。

### 4.4. 作業単位と中断再開

- [作業単位の方針](work-session-policy.md)に従い、各工程を30〜60分へ分割します。例えば保存機能のテスト先行作成、実装、再起動後の評価を別の作業単位としてつなぎます。未決の保存方式を先に固定せず、確定した仕様から具体化します。
- 途中保存、翌日の再開、`/compact` 前後の照合、`/clear` 後の開始、サブエージェントの起動依頼と結果回収についても、同じメモ管理アプリの作業 ID・ファイル・承認状態を使う具体プロンプトを用意します。

## 5. 文書と検証記録の配置

読者向け資料と検証記録は、次の配置を予定しています。

| 配置先 | 内容 |
| --- | --- |
| `manual/prompts/generic/` | 別のアプリへ置き換えて使う汎用プロンプト |
| `manual/examples/memo-manager/` | 読者向けの題材説明と、工程を通して追える実践例 |
| `manual/examples/memo-manager/prompts/` | メモ管理アプリを作るための具体プロンプト |
| `manual/examples/memo-manager/documents/` | 要件・仕様・設計などの記入済み成果物の例 |
| `authoring/validation/` | 実際に入力した文面・追加指示、実行条件、結果、手順書・プロンプトの修正記録 |

各工程の本文にも、対応する汎用・具体プロンプトを正本から転載します。プロンプト ID・版・掲載先を対応付け、公開・更新時に正本との一致を確認します。転載を独立した編集元として扱いません。

上記は手順書側の配置です。題材アプリのリポジトリは別の作業場所として、ソース・アプリ用の仕様書・テスト・CI 設定を管理します。その場所は、初期化の具体プロンプトを執筆する前に決めます。

## 6. 検証で確認すること

### 6.1. 工程と成果物

掲載した具体プロンプトを Codex に実際に入力し、前提の文書と指示から次の成果物を作れることを確かめます。入力の補足が必要だった箇所、質問が増えた理由、`AGENTS.md` の更新漏れ、実装ルールの逸脱や検査結果を記録し、手順書とプロンプトへ反映します。

RC と正式リリースの進め方、品質の判定は[作成方針](creation-policy.md#14-作成と品質確認の進め方)に従います。RC の NG から修正・再評価へ戻る経路と、正式版成果物の確認も検証対象です。結果にはプロンプト・手順書の版と実行環境を付け、確認できた組み合わせを示します。

要求・設計・テスト仕様のユーザー承認、テストコード作成前に hooks が機能した記録、未実装段階のテストと実装後の成功結果、RC タグ CI、ユーザー記入の手動評価、不具合レポートのレビュー、正式版タグ CI のつながりも確認します。デスクトップ全体の E2E と、UI・バックエンドの一部のテストは、確認できた範囲を分けます。

### 6.2. 配布物と支援ツール

RC と正式版は CI の配布物を導入して確認します。メモを保存して再起動後も利用できること、開発用環境に依存せず起動できること、失敗時の扱いなどを、承認した仕様に従って評価します。正式版は公開前に確認し、同じ成果物を配布します。レビューで補った確認観点は、[レビュー記録](review-notes.md)に記載しています。

Windows 11 amd64 の日本語環境で Taskfile と Go ツールを実行し、日本語データ・空白を含むパス・失敗時の終了コード、生成した Excel の14列・表示・結果の保護を確認します。CI では Go・task を用意して同じタスクを実行します。性能要求を設けた場合は、要求の判定基準と実際の対象・条件を対応付けて測定し、未実施の計測を実証済みとしません。

Taskfile の生成・ビルド・テストの順序、製品・UI・支援ツールの検査対象、フックの入出力と拒否を確認します。手動ケースは一つの編集元から Excel へ生成し、環境を増やす場合も同じケース ID の結果を区別できることを確認します。性能要求があれば閾値の判定も確かめ、計測コマンドが成功したことだけで合格にしません。

### 6.3. 作業時間と中断再開

作業時間の見込みと実績、待ち時間、中断時に保存したチェックポイント、同じ会話・新しい会話・圧縮後の再開、サブエージェントの起動・回収・途中停止も検証します。未完了のテストや手動評価を保存して再開でき、工程全体の承認・完了と混同しないことを確認します。

保存機能のテストを途中で止めた例では、未実装による想定内の失敗と未実行を分け、次の実装から再開できることを確認します。RC の手動評価をケースの途中で止めた例では、版・データ・前提条件を照合し、必要ならそのケースの最初からやり直します。タグ送信・公開の結果が不明な中断も、リモートの実施済み状態を確認して再開する検証対象にします。
