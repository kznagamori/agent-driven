# 既存アプリケーションの機能追加・改修版への引き継ぎ事項

作成日：2026-10-15  
更新日：2026-10-15  
状態：将来の執筆に向けた記録。改修版の手順書本体は未着手。

## 1. 着手する順序

まず新規アプリケーション作成の手順書を作ります。内容のレビューに加え、代表的なデスクトップアプリを一つ、その手順書に沿って作成・リリースして品質を確認します。

その結果を人が確認し、問題ない品質と判断してから、既存アプリケーションの機能追加・改修を扱う手順書を作成します。[改修版へ進む判定条件](creation-policy.md#142-既存アプリケーションの改修版へ進む判定)を基準にし、補足資料の執筆・検証状況も併記します。

最初の題材は Go＋Wails v2 のメモ管理アプリです。確定した内容と残件は、[想定アプリケーション](example-application.md)を参照します。

新規作成版でも、RC 評価で見つかった不具合の修正と再評価は扱います。ここで後から作るものは、既に存在するアプリケーションへの変更を開始するための、現状調査や影響分析を含む手順書です。

## 2. 新規作成版から引き継ぐ方針

### 2.1. 要求・仕様・承認

- 人が変更のアイデアを示し、AI が要件・仕様を整理して、人が節目で確認する。
- 関連する質問をまとめ、細部には理由付きの推奨案を仮置きし、質問の終了条件を設ける。
- 類似機能の共通ルールと例外を明示し、仕様の矛盾を防ぐ。
- 仕様、設計、実装タスク、テスト、人の評価項目の対応を保つ。
- 要求・設計・単体テスト要件・E2E テスト仕様の AI レビューとユーザー承認、承認後の変更時の再確認を引き継ぐ。テストコード作成前に hooks を整備し、手動評価 `.xlsx` と結果を要求 ID で追えるようにする。[開発の手順指針](development-workflow.md)を基に、既存テストへの適用と必要な差分を検討する。

### 2.2. AI・指示・開発支援

- Codex を主とし、Claude Code への適用差分を確認する。
- 自作する開発支援ツールは Go、タスクランナーは task（go-task）とし、開発ホストは両方の導入済みを前提にする。[開発支援ツールの方針](creation-policy.md#123-開発支援ツールと-task)を引き継ぎ、既存の実行方法を調査したうえで Taskfile との対応・移行範囲を明示する。
- 設計判断に必要な実証は承認前に限定して行い、既存の環境・hooks・Go ツールを再利用する。Taskfile の実行順序と検査対象、hooks のイベント別の拒否形式、E2E ケースの一つの編集元と環境別評価、性能要求の達成条件を引き継ぐ。
- 要件・仕様・設計・実装・リリースの節目で、開発対象リポジトリの `AGENTS.md` の更新要否を確認し、必要な差分と更新後の再読・適用確認を扱う。
- 各工程に汎用プロンプトと具体プロンプトを対で用意する。改修版でも、対象アプリと変更内容を執筆前に決め、Codex に実際に入力する具体版を作る。
- 実装ルールの再確認と、hooks・変更後・CI の検査を組み合わせる。具体化の基準は、[実装ルールと hooks の方針](creation-policy.md#11-hooks-による実装ルールの再確認と検査)を参照する。

### 2.3. 技術構成とリリース運用

- 指定された言語・フレームワークと、Windows 11 amd64 を必須、Ubuntu 対応をアプリごとに決める方針を引き継ぐ。[技術構成と対象環境](creation-policy.md#12-技術構成と対象環境)を基準にする。
- 家庭内 LAN の Web アプリは、1台の共通 Caddy による配信・転送、IP アドレスでの HTTPS、内部 CA による証明書管理と利用端末の信頼登録を引き継ぐ。Caddy ホストは Windows 11 amd64 と Ubuntu 24.04 LTS の amd64／arm64 のケースを扱う。[HTTPS と共通 CA の方針](creation-policy.md#13-家庭内-lan-の-https-と共通-ca)を参照する。
- 開発、RC 評価、修正・再評価、正式リリースは、[作成方針のリリースフロー](creation-policy.md#7-開発評価リリースの基本フロー)を基にする。ユーザーのタグ送信を契機とする CI、ユーザーの不具合レポートレビュー、必要なテストだけの変更、PR・マージ・正式版タグの担当を引き継ぐ。
- 機能単位のテスト先行と実装の反復、公開しない CI の早期実行、正式版の未公開作成・確認後の同一成果物の公開、配布物の導入・復旧とブランチ整理を引き継ぐ。改修版では既存環境・雛形・履歴を調査して使い、作り直さない。
- 承認の意味が変わらない修正には再承認を要求せず、文書の分割数や AGENTS.md の更新、検査・回帰テストは変更の影響に合わせる。レビューで修正した理由は、[レビュー記録](review-notes.md)を参照する。

### 2.4. 作業単位と中断再開

- 大きな工程を30〜60分の作業単位へ分けること、途中保存と再開、会話の切り替え・圧縮、サブエージェントの起動・結果回収・終了は、[作業単位の方針](work-session-policy.md)を引き継ぐ。既存アプリの調査も、対象・結論・次の調査を残せる小さな単位へ分ける。
- チェックポイントは変更分を中心とし、作業・工程・承認の状態を区別する。レビュー・テスト結果の対象版、実行済みのタグ・PR・公開、途中で止まった評価の前提条件を照合して再開する。

## 3. 新規作成版の執筆・検証中に残す情報

検証記録は、内容が生じた時点で `authoring/validation/` に追加します。以下は記録する項目の案です。

| 残す情報 | 改修版での利用目的 |
| --- | --- |
| 実践検証に使った手順書の版、環境、ツール、アプリの範囲 | どの前提で成立した手順かを判断する |
| 採用した技術構成・版、対応 OS・CPU、動作確認した環境 | 改修後にも維持する対応範囲と依存関係を判断する |
| Go・task の版、Taskfile と Go ツール・依存の配置、Excel 生成元、検証・計測の条件・結果、ホストと CI での実行記録 | 既存の支援ツールと実行方法を調査し、生成物や性能評価を同じ条件で再確認する |
| 実装ルール、hooks の再確認・検査・停止・復帰の記録 | 既存ルールへの適用方法と、検査で防げた逸脱を引き継ぐ |
| `AGENTS.md` を更新した節目、理由、差分、再読・適用確認の結果 | 改修内容に合わせた指示の更新と、既存の規則を整合させる手順に活用する |
| 汎用・具体プロンプトの ID・版・掲載先の対応、実際に入力した文面、追加質問への回答・追加指示 | 改修版でも実際に入力できる文面と、工程間の成果物のつながりを用意する |
| アイデアから要件へ変換した記録 | 変更依頼から変更仕様を作る方法に応用する |
| 質問のグループ、質問回数、追加質問の理由、仮置きの採否 | 既存仕様の確認が発散することを防ぐ |
| 機能の共通ルールと例外 | 既存機能と追加機能の整合を確認する |
| 仕様・タスク・テスト・評価項目の対応 | 変更の影響範囲と必要な回帰確認を追う |
| 要求・設計・テスト仕様の承認記録、テスト先行時の実行状態、要求 ID と単体・E2E 自動・手動の結果の対応 | 既存の承認済み範囲を確認し、必要なテストだけを変更して再承認・回帰確認へつなぐ |
| 手動評価 `.xlsx` の版・評価回ごとの結果、不具合・修正内容レポートとユーザーレビュー | 評価結果を上書きせず、修正前後の確認と判断を追跡する |
| 作業単位の時間・分割実績、チェックポイント、会話の切り替え・圧縮後の再開、サブエージェントの起動・回収・停止の記録 | 既存の差分・承認・確認結果を保ち、翌日や別の会話から同じ範囲の調査・改修を再開する |
| RC 評価時の不具合、再現手順、原因、修正、再評価 | 改修時の不具合対応と再発確認の手順に活用する |
| 仕様変更が発生した際の判断と、更新した文書 | 変更管理の方法を具体化する |
| 手順書に不足していた説明、誤解、作業の戻り、改善結果 | 改修版で同じ問題が起きることを防ぐ |
| RC と正式版のバージョン、ソース・依存関係・ビルド条件、CI、成果物、配布前の確認結果 | 再ビルドの差分と評価結果を追い、既存のリリース運用を調査・継承する際の観点にする |
| Web 向けの検証で使った CA の識別情報、接続 IP、証明書の更新・信頼登録の手順 | 既存の共通 CA と端末の信頼関係を保ってアプリを改修する。秘密鍵は文書に記録しない |
| 共通 Caddy の版・ホスト OS／CPU・ルーティング設定、データ保存先・復元手順の参照、接続の確認結果 | アプリ追加・改修時に、共通 Caddy と内部 CA、他のアプリへの影響を確認する |

実践検証の実績はまだありません。結果が得られた時点で、記録へのリンクと再利用できる内容を追記します。文書レビューで確認した項目と、実際に手順を実行した項目は分けて記録します。

## 4. 改修版で追加して検討する事項

以下は今後の検討項目です。改修版の必須工程として確定したものではありません。

| 検討項目 | 確認・整理する内容 |
| --- | --- |
| 現状の把握 | リポジトリ構成、実行方法、既存の仕様書、テスト、CI、配布方法 |
| 既存ルールと検査 | `AGENTS.md` などの指示、実装ルール、既存 hooks、リンター・依存関係検査の適用範囲 |
| 指示ファイルの更新 | 既存の手書きの規則や上位・下位ディレクトリの指示を確認し、変更仕様・設計・実行方法に合わせて差分を反映する方法 |
| 具体プロンプトの題材 | 新規作成版のメモ管理アプリへ変更を加える例にするか、別の既存アプリを扱うかを、改修版本文の執筆前に決める |
| 技術構成と対応環境 | 採用済みの言語・フレームワークの版、Windows／Ubuntu と CPU の対応範囲、更新の必要性 |
| 既存仕様の確認 | 文書、コード、実際の動作が食い違う場合の調査・確認方法 |
| 変更前の状態 | ビルド・テスト・主要機能の確認結果と、既知の不具合 |
| 変更の範囲 | 追加・変更・維持する振る舞いと、今回扱わない範囲 |
| 影響分析 | 関連機能、共通ルール、データ、インターフェース、依存関係への影響 |
| 互換性 | 既存の利用方法・データ・外部連携への影響と、人が確認する事項 |
| 仕様の更新 | 現状仕様と変更後仕様の記録方法、更新対象の文書 |
| 回帰確認 | 変更箇所と、維持すべき既存機能を確認する方法 |
| データ変更 | データ移行や設定変更が必要な場合の検証方法 |
| 既存運用への適用 | 現在のブランチ・CI・リリース運用に合わせる方法 |
| Caddy・LAN・共通 CA | 既存 Caddy のルーティング・データ保存・内部 CA、IP と証明書、端末の信頼登録、変更による他アプリへの影響 |
| 問題時の復旧 | 変更やリリースを戻す必要がある場合の手順と条件 |

既存仕様が文書化されていない場合は、調査結果を推測・確認済みの事実・人に判断を求める事項に分ける方法も検討します。

## 5. 改修版の作成を始める際の確認

1. 新規作成版の品質確認結果と、残った制約を確認する。
2. この文書と実践検証の記録を読み、再利用できる手順・ひな型を選ぶ。
3. 対象にする既存アプリと、その現状の文書・テスト・CI を確認する。
4. 改修版で追加する工程と品質の判定方法を決める。
5. `manual/existing-development/` に本体を作成し、共通部分への参照を整備する。
