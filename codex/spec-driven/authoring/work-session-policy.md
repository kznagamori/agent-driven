# 作業単位・中断再開・AI コンテキストの運用方針

作成日：2026-10-15  
更新日：2026-10-15  
状態：作業単位・中断再開・AI コンテキストの執筆用運用案。実践検証は未実施。

## 1. この文書の役割

個人開発の平日の作業時間は1〜4時間を想定します。[開発の手順指針](development-workflow.md)の大きな工程を、30〜60分で保存・終了できる作業単位へ分割し、途中で中断しても再開できる方針を定めます。

工程内を小さな作業単位へ分ける方式を採用します。工程番号ごとの全成果物を1時間で完成させる方式ではありません。実行用の作業票・引き継ぎテンプレート、各工程の汎用・具体プロンプトは、`manual/` の執筆時に作成します。

## 2. 30〜60分の作業単位

### 2.1. 区切る基準

作業単位には一つの確認可能な目的を持たせ、読み込み、作成・変更、関係する確認、結果保存、再開用の記録を含めて30〜60分に収まるよう計画します。30分より短い承認・タグ操作などを、時間を埋めるために引き延ばしません。60分を超えそうな作業は、着手前に分割します。

作業 ID は、工程番号と枝番で識別する案とします。例えば工程8を `08-01`「画面と操作の仕様」、`08-02`「データの設計」のように分けます。工程・要求・テストの ID と、作業単位の ID は使い分け、要求やテストの ID を分割の都合で振り直しません。

| 作業票の項目 | 記載内容 |
| --- | --- |
| 作業 ID・工程 | 元の工程番号、今回の小さな目的、前提となる作業 |
| 入力 | 参照する指示・仕様・承認記録と版、対象リポジトリ・ブランチ |
| 対象範囲 | 今回扱う要求・テスト・ファイル、今回変更しない境界 |
| 時間の見込み | 開始・終了予定時刻、30〜60分以内の作業時間、外部の待ち時間の見込み |
| 成果物と確認 | 保存先、実行する確認、完了条件、未完了時の扱い |
| AI の利用 | 同じ会話を継続するか、`/clear`・`/compact` の候補、サブエージェントの要否・担当 |
| 中断・再開 | 引き継ぎの保存先、次に行う一つの操作 |

作業票は実装計画の行やチェックポイントの節にまとめられます。小さな作業ごとに、別の管理文書を増やすことは必須にしません。

作業単位の状態は「未着手・進行中・確認待ち・完了」で管理し、工程全体の承認・完了とは別にします。例えば「CI を開始して実行 ID を保存する」が目的の作業は完了できますが、結果確認の作業とリリース工程は未完了です。各作業の依存先を示し、未確認の結果が必要な作業へ先に進まないようにします。

### 2.2. 時間内に終える運用

45〜60分の作業なら、最後の5〜10分を確認と保存に確保する案を基本にします。残り時間で完了できないと分かった時点で、対象を分割し、完了部分・未完了部分と次の作業を記録します。時間切れを理由に、未検査の成果物を完了・承認済みにしません。

人の回答待ち、ダウンロード、ビルド、CI などの待ち時間は、手を動かす作業と分けて記録します。総経過時間が60分を超える場合も、その日の操作は実行 ID と状態を保存して区切り、結果確認を次の作業単位へ分けます。工程の意味上の完了条件は、必要な結果がそろうまで未完了のまま維持します。

一回のビルドなど分割できない処理は、実行開始・待機・結果確認を管理できる形にします。継続できる処理は状態確認の方法を残し、終了すると失われる処理は停止・再実行の方法を記録します。60分という計画値から、外部サービスや AI の応答時間まで保証できるとは扱いません。

待つ間も人が画面を見続ける必要がある場合は、その時間も当日の枠に含めます。結果確認を次へ分けられるのは、実行先・状態・後から確認する方法が特定できる場合です。見込み時間を超えた調査では、分かった事実・試した方法・未確認の仮説を残し、次の確認を一つに絞ります。同じ方法を根拠なく繰り返して作業単位だけを増やしません。

### 2.3. 平日の組み合わせ例

| 確保できる時間 | 組み合わせの例 |
| --- | --- |
| 1時間 | 45分の作業単位を一つ、残りを休憩・予備時間にする |
| 2時間 | 45分の作業単位を二つ、残りを休憩・予備時間にする |
| 4時間 | 45分の作業単位を四つ、残りを休憩・予備時間にする |

これは予定の例です。30分単位を組み合わせてもよく、その日に複数の工程を終えることは必須にしません。ユーザーは作業単位の途中でも中断でき、その場合も第3節の保存を行います。

開始時に、当日の時間枠と実行してよい作業単位をまとめて指定できます。その範囲内なら、各単位の結果を保存して次へ進め、単位の境界だけを理由に毎回の承認を増やしません。仕様などの承認待ち、ユーザーの操作待ち、当日の終了時刻に達した場合は、保存して区切ります。一つの作業だけを依頼された場合は、その範囲を保ちます。

## 3. 中断と再開の記録

### 3.1. ファイルを再開の基点にする

仕様・設計・テスト仕様・承認記録は、それぞれの正本で管理します。現在の作業を再開するための情報は、会話外のチェックポイントへ簡潔に保存します。`AGENTS.md` には再開時の読み順と正本の場所を記載し、毎回の作業ログ全文を蓄積しません。

アプリ側の配置例は `docs/work/plan.md` と `docs/work/checkpoint.md` です。これは配置案で、手順書側の `authoring/` と区別します。初期準備で一つの配置を決め、同じ情報の正本を複数にしません。

| チェックポイントの項目 | 保存する内容 |
| --- | --- |
| 現在地 | 工程・作業 ID、目的、作業単位の状態と工程全体の承認・完了状態 |
| 作業場所と差分 | リポジトリ、ブランチ、基準コミット、未コミットの変更先と意図。コミット未作成ならその状態 |
| 参照と判断 | 適用指示、承認済み文書・版への参照、決定事項と仮置き・未決事項の区別 |
| 成果物 | 保存済みファイルと、変更・作成・レビューした範囲 |
| 確認結果 | 実行対象のコミットまたは変更状態、環境・コマンド、成功・失敗・中断・未実行、未実装による想定内の失敗。詳細ログは参照先 |
| 実行中の処理 | CI 実行 ID、ローカル処理の識別情報、終了・継続・再実行の判断と状態確認の方法 |
| サブエージェント | 役割・対象・識別情報・終了状態、採用した結果の保存先、未回収の結果 |
| 次の操作 | 再開時に最初に行う一つの操作、残件、進める条件・ユーザー判断が必要な事項 |

実行記録には、task のタスク名・引数・入力と、結果・ログの参照を残します。Go・task の版や Taskfile は共通の環境記録を参照し、変更した場合に更新します。Excel 生成や性能計測などの Go ツールの作成も、実装・検査・結果保存を含めて作業単位へ分けます。採用と適用範囲は[開発支援ツールの方針](creation-policy.md#123-開発支援ツールと-task)に従います。

通常の更新は「作業 ID と状態・変更と保存先・確認済み／未確認・次の操作」を短く記載します。環境・指示・承認など変わらない情報は参照を共用し、実行中の処理・サブエージェントは該当する場合だけ追記します。表の全項目を毎回コピーし直す形式にはしません。基準コミットは作業開始時などの比較元を示し、この記録自身を含むコミットの ID を本文へ書き戻すことは要求しません。

人の判断・承認、新しく分かった重要な制約、実行結果は、作業の終了時まで会話だけに置かず、その時点で正本または結果の記録へ反映します。正本への反映待ちがある場合は、対象と未反映の状態を残します。チェックポイントだけで要求を変更・承認済みにしません。

### 3.2. 中断する順序

1. 新しい変更や長い処理の開始を止め、保存する範囲を定める。
2. 編集中のファイルを保存し、差分と実行中の処理を確認する。
3. サブエージェントがいる場合は、第5.3節に従って結果を回収するか、停止と途中保存を依頼し、現在の状態と未回収の結果を記録する。
4. チェックポイントを更新し、完了条件を満たした部分と途中の部分を分ける。未実行の確認も明記する。
5. 必要な場合だけコミットする。作成した場合は、コミット後の差分と基準との対応も記録する。中断のたびのコミットや、途中の作業を完成扱いすることは要求しない。
6. 保存先と次の操作をユーザーへ示して区切る。会話を整理する場合は、保存後に第4節の操作へ進む。

突然の終了で保存手順を行えなかった場合は、再開時に実ファイル・Git 差分・CI の状態を調べ、最後の記録以降の変更を確認します。失われた情報を推測で承認済みにしません。

通常の再開は、保存した作業ディレクトリが残っている環境を前提にします。別の端末へ移る場合は、未コミット差分・未追跡ファイル・必要な評価データを移せる方法を別途用意し、コピーやコミットに含めない機密情報を区別します。会話履歴や基準コミットだけで途中の編集まで復元できる扱いにはしません。

### 3.3. 再開する順序

1. 作業先・ブランチ・コミット・未コミット差分を確認し、チェックポイントとの違いを把握する。
2. 適用される `AGENTS.md` と詳細ルール、今回の仕様・設計・テスト仕様、承認記録を読み直す。hooks の対象・設定も確認する。
3. 前回から変化したファイル、CI の完了状態、サブエージェントの残件を確認する。保存済みのテスト結果が現在の変更へ適用できるか判断する。
4. 今回の目的・時間・対象範囲・完了条件・次の操作を明示し、作業を再開する。必要な確認は行い、関係のない検査を中断のたびに全件再実行しない。

承認の状態は会話の要約だけで判断せず、保存した承認記録へ照合します。同じ会話へ戻った場合も、この確認を省略しません。

実行したか不明な操作は、現在の状態を調べてから再試行します。特にタグ送信・PR・マージ・公開は、リモートのコミット・タグ、CI 実行、PR・公開状態を先に照合し、完了済みなら結果確認から再開します。操作の担当はユーザーのまま維持します。再試行するために既存タグを付け替えたり、同じ公開を作り直したりしません。

中断したテストは未完了として扱います。自動テストは実行終了と結果の有無を確認し、結果がない場合は前提を整えて再実行します。手動テストの途中状態を復元できなければ、そのケースの前提条件からやり直します。確認済みのケースまで一律にやり直さず、版・環境・データの変化による影響から再実施範囲を決めます。

過去の成功結果を使う場合は、対象ソース・設定・依存関係・環境が今回も対応していることを確認します。関係する変更があれば、その範囲の検査をやり直します。記録や体裁だけの変更を理由にすべての検査を繰り返す運用にはしません。

## 4. `/clear`・`/compact` と会話の再開

### 4.1. Codex CLI での使い分け

以下は Codex CLI を基本とする運用案です。`/clear` は新しい会話を開始し、`/compact` は現在の会話を要約してコンテキストを整理する操作です。コマンドの意味は [OpenAI 公式ドキュメント：Developer commands](https://learn.chatgpt.com/docs/developer-commands)で確認します（確認日：2026-10-15）。

| 状況 | 基本の扱い | 実行前後に行うこと |
| --- | --- | --- |
| 同じ目的の短い作業を継続する | 同じ会話を使う。時間の区切りだけでコマンドを実行しない | 作業単位の結果と次の対象を更新する |
| 同じ目的の調査・修正が長くなり、会話・ログが増えた | `/compact` を候補にする | 先に判断・残件・次の操作を保存し、実行後に正本とチェックポイントを再確認する |
| 要求承認後に設計へ移るなど、目的・主な入力が切り替わる | 保存と引き継ぎが済んでいれば `/clear` を候補にする | 引き継ぎ・承認・必要なレビュー結果を保存し、実行後は次の作業の開始／再開プロンプトから読む |
| 別機能・別不具合に移り、以前の探索が不要になる | 新しい会話への切り替えを検討する | 対象ファイルの差分を確認し、今回の範囲を再指定する |
| 同じ作業を翌日などに継続する | 保存した会話を再開するか、新しい会話から記録を読む | どちらの場合も第3.3節の確認を行う |

`/clear`・`/compact` はユーザーが CLI に入力する操作として記載します。AI は実行前の保存と、実行後にユーザーが入力する開始／再開プロンプトを用意します。再開後は記録を読み、今回の目的と差分を照合して続けます。AI がファイルを保存したことを、CLI の操作まで実行した証拠にはしません。毎工程で両方を順番に実行する手順にはしません。

保存済み会話への復帰は `/resume` または `codex resume` など、対象版の操作を手順書へ記載します。会話の再開方法と、ファイルからの復旧手順を両方用意します。CLI 以外では新規チャット・履歴からの再開など、対応する操作と検証した利用形態を明示します。

### 4.2. 実行する前の条件

進行中の編集・ツール呼び出しと、サブエージェントの状態を確認してから会話を整理します。判断・承認・差分・未実行の確認・次の操作を、先にファイルへ保存します。手動の操作は、ツールが受け付ける区切りで行います。要約に残ったはずという理由だけで、未保存の判断を引き継いだ扱いにはしません。

`/clear` 後は次の目的に必要な指示と正本を読み直し、`/compact` 後も、今回適用する規則・要求・承認・残件を正本へ照合します。自動圧縮が起きた場合は、進行中の作業を把握できる区切りで照合します。短い圧縮のたびに全工程の計画や承認をやり直すのではなく、適用ルール・対象・残件を確認します。hooks で補助する場合は、開始・再開・圧縮後のどのイベントが対象かを、実際のツール・版で確認します。

利用者の画面で確認できるコンテキスト量と会話の内容を判断材料にし、特定のトークン数・使用率・経過分数での実行を一律に強制しません。上限が近づいてから保存を始めず、作業単位ごとに正本とチェックポイントを更新します。

### 4.3. Claude Code への適用

Claude Code にも `/clear`・`/compact`・会話の再開操作があります。対応する設定・利用形態・版、圧縮時に保持される情報と指示の読み込みを別途確認します。共通の保存・再開条件を保ち、コマンドの引数や画面操作を Codex の例からそのまま転記しません。[Claude Code 公式ドキュメント：Commands](https://code.claude.com/docs/en/commands)（確認日：2026-10-15）。

## 5. サブエージェントの起動・回収・終了

### 5.1. 使う条件

主担当が仕様・判断・統合を管理し、独立した調査やレビューをサブエージェントへ委任する形を基本案とします。短い操作、依存関係が強い連続作業、ユーザー承認の代行には使いません。起動・入力の整理・結果の確認と統合も、作業単位の時間に含めます。

最初は読み取り中心のレビュー担当を1体使う例から示し、並列化が有効な場合だけ増やします。すべての工程で起動することは必須にしません。対象機能の利用可否と上限を確認し、使えない環境では主担当が同じ観点のレビューを行う手順を示します。

Codex で使う場合は、対象工程のプロンプトに起動・委任を明示します。単に担当者へ切り替える操作と、実際に起動を依頼する操作を区別します。例えば `/subagents` の画面・スレッド操作と、自然言語での起動依頼を使い分けます。追加の利用量と調整の時間も見込みます。[OpenAI 公式ドキュメント：Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)（確認日：2026-10-15）。

### 5.2. 委任に含める情報

| 項目 | 内容 |
| --- | --- |
| 目的と区切り | 一つの調査質問またはレビュー観点、対象作業 ID、時間内に返す範囲 |
| 入力 | リポジトリ・ブランチ、レビュー対象のコミットまたは未コミット差分を含む保存状態、対象ファイル、適用指示と承認済み文書への参照 |
| 変更権限 | レビューのみか、どのファイルを編集できるか。実行可能な検査と制約 |
| 出力 | 指摘の根拠・場所・影響、実行した確認、未確認点、変更した場合のファイルと結果 |
| 終了条件 | 結果を返す条件、主担当が待つ結果、途中終了時の保存、再委任の要否 |

親の会話をすべて共有しているとは仮定せず、必要な文書と制約を明示します。Claude Code の通常のサブエージェントと fork など、コンテキストの渡り方の違いも、ツール別の補足で確認します。[Claude Code 公式ドキュメント：Subagents](https://code.claude.com/docs/en/sub-agents)（確認日：2026-10-15）。

### 5.3. 結果の統合と中断

レビュー担当は原則として読み取りのみとし、主担当が修正を反映します。複数の担当が同じファイルを同時編集する構成を避けます。並列実装を採用する場合は、独立した変更範囲または作業ツリーと統合担当を決め、各作業場所で指示・hooks・検査が有効かを確認します。

読み取りのみという依頼と、ツールが実際に制限する権限は区別します。起動時に利用可能なツール・権限を確認し、親から継承する設定と作業指示の範囲を記載します。依頼文だけで別の読み取り専用環境が作られたとは扱いません。[OpenAI 公式ドキュメント：サブエージェントの権限](https://learn.chatgpt.com/docs/agent-configuration/subagents#approvals-and-sandbox-controls)を参照します。

読み取りのレビューでも、対象ファイルは保存してから渡し、レビュー中はその対象の変更を止めるか、固定した版を別の作業場所で確認します。主担当は対象外の独立した作業を進められます。レビュー後に対象を変更した場合は、変更部分と関連箇所を再確認し、以前の結果を更新後の全体へ無条件に適用しません。

主担当は返却された根拠と対象版を確認し、採用・保留・不採用と理由を記録します。必要な結果が未回収の作業をレビュー完了にせず、依存しない作業だけを進めます。人が担う承認・タグ送信・PR・マージ・公開の役割は変更しません。

ユーザーが作業の中断・終了を指定した場合や、`/clear` による別の会話への移行前には、結果を回収・保存して終了するか、停止と途中報告を依頼します。停止を確認できなければ未確認として記録し、同じ対象を変更する作業を始めません。回収待ちだけで当日の時間枠を延長せず、未回収の結果は次の作業で扱います。

同じ目的での `/compact` や連続した作業単位の境界では、対象版・担当・実行状態を確認でき、当日の時間枠内ならサブエージェントを継続できます。圧縮や区切りのたびの強制終了・起動し直しは要求しません。別の会話やセッションの終了後まで実行状態を引き継げるとは仮定せず、必要な場合は保存した依頼・途中結果から新たに起動します。無制限な追加起動や、目的を広げる再委任は行いません。

## 6. 開発工程ごとの分割と AI の利用案

以下は本編を執筆する際の設計例です。すべての工程を対応させ、実際のファイル名・操作・所要時間は題材アプリで検証して記載します。各行の全作業を一回で実行する意味ではありません。

ユーザー承認の節目は分割後も維持します。文書の一部を書いたことと、工程全体が承認されたことを区別します。手動 E2E も評価回と対象 RC を固定して途中結果を保存し、未実施ケースを残したまま完了にしません。

## 7. 手順書とプロンプトへ記載すること

各作業単位の本文には、見込み時間、入力、今回の目的、成果物と確認、中断時の保存先、再開時の操作、コンテキスト操作の要否、サブエージェントの担当を記載します。コマンドを使わない場合も「同じ会話を継続」と明示し、読者が毎回判断をやり直さずに済むようにします。

汎用・具体プロンプトには、通常の開始だけでなく、中断保存、再開、`/compact` 前後、`/clear` 後の開始、サブエージェントの起動依頼・結果回収を用意します。具体版ではメモ管理アプリの同じ要求・作業 ID とファイルを使い、保存した状態から次へつながる例にします。操作コマンドと、AI に渡す依頼文を区別します。

開始・再開の依頼文には「依頼された作業単位または当日の作業一覧」「時間枠と見込み」「残り時間に応じた分割と保存」「承認待ちの箇所を越えない条件」を含めます。サブエージェントを使う依頼文には、明示的な起動、人数・役割・入力・変更可能範囲・返却結果・終了条件を含めます。共通の条件を開始時に提示した後は、変更した対象・今回の保存先などの差分で依頼できる形にします。

## 8. 実践検証と更新

題材アプリで、予定と実際の作業時間、待ち時間、分割し直した理由、保存・再開に要した時間を記録します。次の日の再開、作業途中の中断、同じ会話への復帰、新しい会話への引き継ぎ、手動・自動の圧縮後の照合、サブエージェントの起動・回収・途中停止を確認します。

実際に使ったツールと版、コマンド・画面操作、引き継いだファイル・状態、失われた情報や補足が必要だった箇所を記録します。時間内に収まらなかった作業は、検査や承認を省くのではなく、粒度と前提を修正して再確認します。検証していない利用形態や、コンテキスト操作の組み合わせを検証済みとはしません。
