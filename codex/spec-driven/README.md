# AI エージェントによる仕様書駆動開発の手順書

このディレクトリでは、同じ進め方でアプリケーションを作成し、評価・リリースまで進められる手順書を作成します。

まず新規アプリケーションの作成を扱い、代表的なデスクトップアプリで手順書を検証します。その品質を確認してから、既存アプリケーションの機能追加・改修を扱う手順書へ広げます。

## 現在の状態

2026-10-15 時点の作成状況は、次のとおりです。

| 対象 | 状態 |
| --- | --- |
| 作成方針・開発の手順指針・配置計画 | 整理・文書レビュー済み |
| 手順書本体・汎用／具体プロンプト・テンプレート | 入口のみ作成。工程別の内容は未執筆 |
| Go 製の支援ツール・Taskfile・hooks・CI の設定 | 未作成 |
| 題材アプリによる開発・評価・リリースの実践検証 | 未実施 |

現在の方針は `authoring/`、レビューの指摘・修正理由と過去の確認結果は[レビュー記録](authoring/review-notes.md)を参照してください。文書レビューと実践検証の状況は分けて管理します。

## 基本方針

| 項目 | 方針 |
| --- | --- |
| 開発の進め方 | 人が簡易なアイデアを示し、AI が要求・仕様・設計を作成・レビューする。ユーザーが節目で承認し、機能単位でテスト先行と実装を反復する |
| 題材とプロンプト | Go＋Wails v2 のメモ管理アプリを使い、各工程に汎用プロンプトと Codex へ入力する具体プロンプトを対で用意する |
| 指示と実装ルール | `AGENTS.md` を初期作成後も見直し、hooks によるルールの再確認・検査・拒否を組み込む。Claude Code への適用差分も扱う |
| 作業時間と再開 | 平日の1〜4時間に合わせ、工程を30〜60分の作業単位へ分ける。途中保存・再開、`/clear`・`/compact`、サブエージェントの運用を記載する |
| 開発支援 | 自作支援ツールは Go、タスクランナーは task（go-task）とする。開発ホストは両方の導入済みを前提にし、ローカルと CI で共通の Taskfile を使う |
| 対象環境 | Windows 11 amd64 を必須とする。Ubuntu 24.04 以降の amd64／arm64 はアプリごとに対応要否を決める。WPF 構成は Windows 向けとする |
| 家庭内 LAN の Web | 共通 Caddy と内部 CA を使い、IP アドレスで HTTPS 接続する。Caddy ホストは Windows 11 amd64、Ubuntu 24.04 LTS amd64／arm64 を説明対象とする |
| 評価とリリース | タグ CI で RC を作り、指定14列の `.xlsx` で手動評価する。修正・再評価後に正式版を作成し、確認した同じ成果物を公開・配布する |

詳細な合意事項と執筆方針は[作成方針](authoring/creation-policy.md)、43工程の順序と担当は[開発の手順指針](authoring/development-workflow.md)にまとめています。

## ディレクトリの役割

```text
spec-driven/
├── README.md
├── authoring/                       # 手順書を作成・改善するための文書
│   ├── creation-policy.md           # 目的、合意事項、執筆方針、品質の判定方法
│   ├── development-workflow.md      # 開発工程の順序、担当、承認・差し戻し条件
│   ├── directory-structure.md       # 配置の理由、現在の構成、将来の拡張先
│   ├── example-application.md       # 具体プロンプトと実践検証に使う題材
│   ├── existing-development-notes.md # 既存アプリケーションの改修版への引き継ぎ
│   ├── review-notes.md              # 指摘、修正、文書レビューと実践検証の区別
│   └── work-session-policy.md       # 30〜60分の区切り、中断再開、AI の会話・委任
└── manual/                          # 開発時に利用する手順書本体
    └── README.md                    # 手順書の入口と作成状況
```

`authoring/` は手順書の作成者が参照する文書、`manual/` はアプリケーションの開発者が参照する文書です。手順書を作る際の議論・判断理由・試行記録は `authoring/` に残します。

題材アプリの開発は、別に定める開発対象リポジトリで行います。手順書に載せる `/init`・アプリ用の `AGENTS.md` 更新・ビルド・CI は、その作業場所で行う操作として説明します。

## 参照先

- 手順書を作成・変更する場合：[作成方針](authoring/creation-policy.md)を最初に確認します。
- 開発工程を執筆する場合：[開発の手順指針](authoring/development-workflow.md)で作業順序、担当、承認と修正ループを確認します。
- 工程を小さな作業へ分ける場合：[作業単位・中断再開の方針](authoring/work-session-policy.md)で時間、保存・再開、AI の会話整理と委任を確認します。
- 文書を追加する場合：[ディレクトリ設計](authoring/directory-structure.md)で配置先を確認します。
- 具体プロンプトや実践検証を準備する場合：[想定アプリケーション](authoring/example-application.md)で題材と残件を確認します。
- 既存アプリケーションの改修版を検討する場合：[引き継ぎ事項](authoring/existing-development-notes.md)を確認します。
- レビューによる修正理由・未検証範囲を確認する場合：[レビュー記録](authoring/review-notes.md)を参照します。
- アプリケーションの開発で利用する場合：[手順書本体の入口](manual/README.md)で作成状況を確認します。

## 編集・確認

文書は日本語の Markdown、ファイル名・ディレクトリ名は英小文字とハイフンを基本にします。ローカル文書へのリンクは相対パスで記述します。

この文書リポジトリには、専用のビルド・テスト環境を導入していません。PowerShell でリポジトリのルートからファイルを確認できます。

```powershell
rg --files spec-driven
Get-Content -Raw -Encoding utf8 spec-driven/authoring/creation-policy.md
```

文書を更新した際は、リンク先、現在の状態、合意事項との整合を確認します。
